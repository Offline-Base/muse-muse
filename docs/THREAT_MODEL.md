# Threat model

What Muse Privacy defends, against whom, with which code, and what is still open. Every table row names a test that exists, or says `Gap:` and why there is none. `tests/test_threat_model.py` fails if a test named here does not exist or is written in a form it cannot look up, if a row's test column has neither a test nor a gap, if a row in "Enforced in code" cites an xfail, if another row cites one without saying xfail, or if the known-gaps list stops matching the xfails in the attack tests.

Reading a test name: a name with a file before `::` is in that file; a name on its own is in `tests/test_attacks.py`; a name that starts with `relay/test/` is a relay test whose title starts with the words after `::` (those run in CI's relay job, not in pytest). To run the Python ones: `uv run pytest -q tests/test_attacks.py tests/test_red_model_view.py tests/test_red_data.py tests/test_threat_model.py`.

This page describes the code on the integration branch as of Oct 31. Three things limit what that means:

- **The live app is older.** It runs earlier code (tag map v1) until a restart window moves it. Daily tag rotation, the narrowed Always approve and the hash manifest are not live until then.
- **The device model today is LFM3-VL-2B, with `DEVICE_ONLY=1`.** Glimmer has not been measured on the device, so nothing here says how it would behave.
- **SAM on scans** (base/regions.py and sidecars/sam/) is built but off by default (SAM_ENABLED) and has not run on real weights, so no row below counts on it.

## What the attack suite is

The attacks are hand-written. `tests/test_attacks.py` and `tests/test_red_model_view.py` are scripted cases on invented data, with the device model faked at the HTTP layer as the worst case a small model can be: a name pass that finds nothing and a labeler that labels nothing. The fake router always wants to share, but with `DEVICE_ONLY=1` the policy decides by default and no model is asked, so that fake is reached only where a test turns model routing on (`DREAMING_BACKEND=prompt` with `ROUTER_TRUST=decide`, in `test_f7_a_router_that_obeys_the_document_cannot_pass_a_floor`). They need no model and no network.

They are not Spark. A harness that had Muse Spark play a hostile Muse (RED-5 to RED-8, RED-12 to RED-14 in docs/SCORE_PLAN.md) was stopped by a safety check and is dropped, not retried. It has no results, and none are implied here. The briefs written for it (`eval/red/scenarios.yaml`) were never run.

So this suite shows what the code does with the attacks someone thought of. It does not show what an adaptive attacker would find. Nothing here attacked a real model: not LFM3-VL-2B, not Glimmer, not Muse. There is no attack success rate, and no attacker was a real person. The eval reports (for example eval/reports/default_loosen_fresh_200_b.md) score decisions on invented items and are not attack results.

## Where model prompts are built

A model whose output can reach Muse must not see a real name, or it could spell one in a form no check knows. These are the places that build a prompt, and what each one sees.

`tests/test_red_model_view.py` records every request in a scripted session (list, search, ask_device, a class summary, grading 24 essays) and checks the first five rows: no roster form or identifier in any of them, every request to a loopback address (`tests/test_red_model_view.py::test_every_model_request_goes_to_this_device`), and the name pass only adds tags. The session never calls the router, since the policy decides by default, so the router row has only its own test. The views do not yet tag a name the roster does not know the first time they read it (finding RED-F7a).

## Residual risk, said plainly

- **Content can re-identify by itself.** A shared snippet that says "my uncle grows taro on the Big Island" points to one student for anyone who knows the class, with every name tagged. The router and the user's approvals decide what is worth sharing; tags do not make content anonymous.
- **Within one day, tags are stable.** With rotation on, a Muse that keeps notes all day can still link what it learns about one tag across calls. Rotation bounds this to the tag's day plus a day and a half, not to one call, and sending a tag back does not extend it.
- **A job released after its tags stopped working.** A run_private_task or ask_device job whose result Muse first asks for after the tags in its instructions stopped working (more than a day and a half after their day ended) is tagged in that day's new tags, so Muse could pair the old tag in its instructions with a new one in the answer. Jobs finish in minutes and Muse asks right away, so this needs a Muse that waits more than a day and a half to read a result.
- **A capital A or I after "student" reads as a code.** An unbracketed "Student A" still restores (the author's call, Oct 31), so "the student I flagged" or "Every Student A Reader" is taken for that tag. While the code is live and sent, the device searches for that real student, and the passages come back to Muse under the tag; once the code has expired, the request gets `EXPIRED_TAG`. It takes a code Muse holds and nothing leaves untagged.
- **A letter home checks tags, not plain text.** Another student's tag or a phone tag is refused, but a name or number Muse wrote out itself goes into the unsent draft for that family (the author's call, Oct 31). Muse can know one if the user typed it in the chat, a folder has names off, or a kind of tagging is turned off. The draft stays on the device until the user sends it, so read it first.
- **The small model labels requests.** With DEVICE_ONLY=1, LFM3-VL-2B labels who a request is for, and the regex floors behind it catch only the phrasings listed in the tests. A paraphrase both miss falls to the first policy rule that matches the result, with no regard for where it is headed: a class-level result goes out as a summary and a tagged score goes out tagged, with no ask, and only what no rule matches asks the user (`test_f3_a_destination_both_miss_follows_the_first_matching_rule`).
- **A summary can still describe someone in other words.** A summary sentence is dropped only for the wordings `router.singles_out` lists. "A student in a wheelchair scored a 4" names no one and stays.
- **Initials are caught in one shape.** Dotted initials within 60 characters of a class word are tagged. "CR" with no dots, initials far from any class word, and initials that are also an ordinary abbreviation ("T.V." and "H.W." on the invented roster, so two of its 24 students) go out as written.
- **Look-alike letters are a short list.** It covers common Cyrillic and Greek letters, no other script. In a text that is mostly not Latin letters, a word made only of look-alikes is left as it is, so a name spelled entirely that way there is missed. Never-share keywords are not folded.
- **Purpose is whatever Muse says.** The device cannot check it. A purpose can make a decision stricter, never looser, but a Muse that lies about an outside destination gets what an honest "for my notes" would get.
- **Approvals are only as good as the reader.** The card shows the exact text that would leave. A user who clicks Share it on everything shares everything that is not refused; the final leak check still runs.
- **A guardian PIN is a lock, not a wall.** It stops a family member from changing the rules or approving results at the device (base/guardian.py). Anyone with an administrator account on the computer can delete `guardian.json`, and a restart locks every browser but changes no rule. It sees nothing typed into Muse, which reaches Meta before the device. With the approvals box off, the family member's approvals still teach dreaming; the toggle's keep words and the floors stay in code either way.
- **The laptop is the trust boundary.** Anyone logged in as the user can read BASE_HOME, the workspace and the approval page (no login on loopback), and on that page /ask shows real names. Use the disk's own encryption and a screen lock. On a Jetson, the page needs a pairing code and a session. The Jetson path is tested in simulation only.
- **The relay sees what Muse sees.** Tagged results and Muse's requests pass through the Cloudflare Worker in the clear inside TLS that Cloudflare terminates. It stores no content, but it is not end-to-end encrypted.
- **No model-driven attacker has been run.** Every attack here is hand-written, so an attack nobody wrote down is not covered. A2 attacks, where Muse knows real names, are tested deterministically only, and roster names can never go to Spark (`Spark.check`).
