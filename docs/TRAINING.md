# Fine-tuning on Lambda

Admin-only fine-tuning jobs that run on the owner's Lambda Cloud account. One job is one GPU instance: the platform launches it with a cloud-init script, the instance trains and reports back, and the platform always terminates it. Lambda bills by the hour from launch until termination, so termination is enforced from three sides: the job's workflow, the job's own "done" callback, and a sweep every 5 minutes. A job only starts while that sweep is configured and has run lately.

Shared types are in `lib/train/types.ts`. Tables are `training_jobs` and `training_events` in `lib/db/schema.ts` (migration `drizzle/0002_training_jobs.sql`), plus `training_datasets` and `training_jobs.eval_summary` (migration `drizzle/0003_training_datasets.sql`), `training_jobs.serve_endpoint` (migration `drizzle/0004_serve_endpoint.sql`), `training_jobs.hub` (migration `drizzle/0006_hub.sql`), and `training_datasets.writer_model` with `training_jobs.judge_model` (migration `drizzle/0008_lab_models.sql`, see Which model did the work).

A job can train on a dataset Muse Wonder writes for a task (see Datasets). A recipe that does, such as `glimmer-lora`, answers the dataset's held-out prompts with the base and the tuned model and sends them back as eval items; once the GPU is shut down, Muse Wonder judges them (see Judging). Before Oct 29, 2026, Muse Spark 1.3 wrote, judged and told the story of everything, and the records say so (see Which model did the work). A recipe can also keep its venv and model weights on a Lambda filesystem in the region (see Model cache). A trained adapter can then be served for a set number of minutes by the `glimmer-serve` recipe, so anyone on its public result page can compare the base and the tuned model live (see Live demo (glimmer-serve)). Once a glimmer-lora job is judged, the platform publishes it to the Hugging Face Hub: the adapter with a model card that says why it was made, and its training data with a dataset card (see Hugging Face Hub).

A glimmer-lora job in decide mode (`mode: "decide"`) trains a decision model instead, on a dataset of a person's labeled examples (`kind: "decision"`, migration `drizzle/0017_decision_datasets.sql`): it is scored by the platform rather than judged, it isn't published, and its live demo picks labels instead of chatting (see Decision models (decide mode), and `docs/DECISION_MODELS.md` for the design).

## Which model did the work

The lab's own model work runs on Muse Wonder (`muse-wonder-1.0`): it writes new datasets (`DATASET_MODEL` in `lib/train/datasets.ts`), judges new runs (`JUDGE_MODEL` in `lib/train/judge.ts`) and tells new Hugging Face stories (`STORY_MODEL` in `lib/train/hub-cards.ts`). Muse Spark 1.3 is never used for new work. The New dataset card prices and times a dataset at Muse Wonder's rates (`WRITER_MODEL` in `components/train/format.ts`).

Each record keeps the model that really did its work:

- `training_datasets.writer_model`: saved when `POST /api/train/datasets` creates the dataset (`DATASET_MODEL`).
- `training_jobs.judge_model`: saved by `judgePlanStep` when judging starts (`JUDGE_MODEL`), before it logs "Muse Wonder is judging N eval items." A job that is skipped or has nothing to judge gets none.
- `training_jobs.hub.storyModel`: saved by `hubStoryStep` with a story a model wrote (`storyBy` keeps the value "spark" for a model's story, its name from before the model was recorded; `storyModel` says which). The template's story has none, and a new why clears it with the story.

Everything made before Oct 29, 2026 was made by Muse Spark 1.3, so a record with no model reads as Muse Spark 1.3 (`lib/train/models.ts`: `writerModelOf`, `judgeModelOf`, `storyModelOf`, shown with `modelLabel`'s names from `lib/format.ts`). History is never relabeled: the first tuned run (Spark wrote its dataset and judged it, the tuned model won 40 of 40) says Muse Spark 1.3 on its pages, its model card, its dataset card and license, and its `muse_muse_run.json`. A job with no judge yet is shown with the judge it will get, Muse Wonder. A dataset Muse Spark 1.3 wrote and Muse Wonder judged names each for its part.

The views carry the model, resolved this way, as optional fields: `DatasetView.writerModel`, `TrainJobView.judgeModel` (null until a judge starts) and `HubView.storyModel`. The pages, the cards (`CardFacts.dataset.writerModel`, `CardFacts.judgeModel`, `GgufFacts.dataset.writerModel`) and the run's record (`dataset.writer`, `eval.judge`, `story.model`, with `story.by` "model" for a story another model than Muse Spark 1.3 wrote) all read them.

## The base model (lib/train/base.ts)

Since Oct 31, 2026 (owner: "Switch outright to r30b") every new glimmer-lora job trains on r30b, Muse Muse's Muse Glimmer 30B with 2026 knowledge, and plain Glimmer is no longer offered:

- glimmer-lora loads `OfflineBase/Glimmer-30B-2026-Knowledge-unsloth-bnb-4bit` at `6f12bf52` (`MODEL` and `MODEL_REVISION` in `GLIMMER_PY`, changed together because `weights_cached` keys on both): nf4 matched to unsloth/Muse-Glimmer-30B-unsloth-bnb-4bit (same 5 shard names, 3,516 tensors, dtypes, shapes and `quantization_config`), public, no token. Jobs before the switch trained on unsloth/Muse-Glimmer-30B-unsloth-bnb-4bit at `ecedda39` (`PLAIN_GLIMMER_MODEL`).
- glimmer-quantize merges into the merged BF16, [OfflineBase/Glimmer-30B-2026-Knowledge](https://huggingface.co/OfflineBase/Glimmer-30B-2026-Knowledge) (`MERGE_BASE`), its 13 shards pinned by SHA-256 as listed at `c06e38cc` (`MERGE_BASE_REVISION`, `BASE_SHARDS`; the weights are the same at `e2b33cce`, its main after that). It has Meta's 1,436 tensor names and shapes (`BASE_TENSORS_SHA256` unchanged, read from the shards' headers). Unsloth finds it from `MODEL`'s name and downloads its main; a merge that fetched anything else leaves no record of those 13 shards and fails.
- The record of a job's base: the jobs route writes `baseModel` (`BASE_MODEL_PARAM`) on every glimmer-lora and glimmer-quantize job it creates (a caller can't set it), and glimmer-lora's done metrics carry `base_model` and `base_revision` (glimmer-quantize's already carry `merge_base`). `recordedBase(job)` reads it back: the param, else the metric, else plain Glimmer. The Hub's checks and cards hold an adapter to the base its job recorded, so one from before the switch is still published as what it is.
- Live demos and local files refuse an adapter trained on plain Glimmer (`adapterProblem`, and `quantProblem` again): the GPU would load it on r30b, which it never trained on. glimmer-publish still uploads one under the base its job recorded. A serve window always loads r30b, so muse-decide's base side answers from r30b too.

Muse Spark Open wrote part of r30b's training data, so r30b and every model trained from it are Derivatives under the Muse Model License. `isSparkOpenDerivative(job)` is the one rule: anything recorded about the job's base (its `baseModel` param, its `base_model` or `merge_base` metric, or the base its adapter_config.json names) is one of r30b's repos. Wherever such a model is shown or shipped it carries the duties:

- "Built with Muse Spark Open", prominently (`BUILT_WITH_SPARK_OPEN`), with the Usage Policy's points (`USAGE_POINTS`): 18 and over only, never presented as written by a person, and its known dangers (made-up answers, going along with false premises). On the result page, the admin job page and the room's result (`SparkOpenNote`), as a chip on the results table and /models' tuned list, and in both live demo boxes, whose GPU loads r30b for every adapter.
- The files: r30b's `LICENSE`, `MUSE_MODEL_LICENSE.md`, `USAGE_POLICY.md` and `NOTICE`, byte for byte from the knowledge branch's `docs/model-licenses/stage-b-r30b/`, are committed in `lib/train/licenses/` (as strings in its `index.ts`, sha256 pinned in `lib/train/__tests__/base.test.ts`). The Hub steps commit the last three beside `LICENSE` in a Derivative's adapter and GGUF repos, whose cards declare `license: other`, `license_name: apache-2.0-and-muse-model-license`, `license_link: MUSE_MODEL_LICENSE.md`. A drive of a Derivative's files (`DriveModel.sparkOpen`) gets `licenses/MUSE_MODEL_LICENSE.md` and `licenses/NOTICE` (its Apache 2.0 and Usage Policy are already the same bytes) and the line atop Start Here.html and README.txt.
- Comparisons on a Derivative's pages and cards read tuned vs "the 2026 Glimmer it started from" (or "r30b"); a job on plain Glimmer keeps "base Glimmer".

## Secrets and trust

- `LAMBDA_API_KEY` stays on the platform (`env.lambdaApiKey`). It is never written into user data, an instance, a sandbox or a product.
- Each job gets a random job token (32 bytes, base64url). The instance gets it in its user data. The platform stores only `hashToken(token)` from `lib/gateway/tokens.ts` in `training_jobs.token_hash`. The token works only for that job's callback and upload routes, and only until 15 minutes after the job ends.
- User data is visible to anyone with access to the Lambda account. That is the owner, so the job token there is fine, and so is a glimmer-serve job's serving key, which is derived from the token's hash (see Live demo (glimmer-serve)). Nothing else secret goes into it.
- Every launch uses the SSH key `muse-muse-platform` (`TRAIN_SSH_KEY_NAME`). Its private key lives only on the owner's Mac at `~/.ssh/muse-muse-lambda`, for debugging. The platform never needs SSH.
- Creating and stopping jobs is admin only (`requireAdminOrAutomation`, so scripts can use `AUTOMATION_SECRET`).
- `HF_TOKEN` stays on the platform too (`env.hfToken`). `lib/train/hub.ts` reads it inside each call it makes to the Hub, so it is never a workflow step's argument or result (step data is persisted), and every Hub error has it blanked out as `[HF token]`. It is never logged, never in user data or a job's params, and never sent to a GPU or a browser. A GPU uploads the adapter's bytes to presigned storage URLs the platform gets from the Hub, which take no credential; those URLs go only to that GPU, in the plan's answer, and are never stored or logged (see Hugging Face Hub).

A job's limits are what the admin asked for, capped by the ceilings; the recipe's defaults (capped the same way) fill in a limit the admin didn't ask for (`clampLimits`). So a recipe can run past its own defaults when the admin asks and the ceilings allow it. `usableMinutes(limits, priceCentsPerHour)` is how long a job can run before either limit stops it: the time limit, or less when the dollar limit runs out first (every started minute counts in full, so $4.29 at $4.29 an hour allows 59 minutes). The runner's deadline is stamped from it (see User data). Cost is `priceCentsPerHour / 100 * hours since launchedAt` (until `terminatedAt`), rounded up to the minute. A job is terminated when its time or dollar limit is reached. When a launch was never saved (Lambda timed out, or the database didn't answer), its clock starts at `createdAt`, which is earlier than the launch, so the limits and the cost are never measured short.

Jobs holding a GPU (compared with `TRAIN_MAX_ACTIVE`) are every job that hasn't ended plus every ended job with `launchedAt` set and no `terminatedAt`. Today's committed spend (compared with `TRAIN_DAILY_USD`) counts every unfinished job at its full dollar limit.

## Lifecycle

```text
POST /api/train/jobs (admin)          -> refused unless the sweep is configured and ran lately (see Routes),
                                         then row "queued", token not made yet, workflow started
trainJob workflow (lib/train/workflow.ts):
  launchStep   launches at most once per job: an instance already listed under instanceName is adopted
               (clock at createdAt); otherwise, for a usesCache recipe, ensureFilesystem(region) (see Model
               cache), then make the token and claimLaunch (queued -> "launching" with the token's hash, in one
               guarded update; only the holder of the claim launches); launch with user data (and the cache
               filesystem mounted), its deadlineEpoch stamped just before the request; save instanceId and
               launchedAt (the time of the request), status "booting".
               429: the claim is given back, retried after 30 s. Other 4xx: claim given back, FatalError.
               Timeout or 5xx: the claim is kept and the retry (2 min later) only adopts the instance by name
               or waits for it, never launches again. maxRetries 3.
               The instance id is returned to the workflow (it isn't secret), so it can terminate by id.
               Database didn't take the instance -> {action: "save"} and saveLaunchStep retries only the save.
               Job ended while the launch was in flight -> the instance is saved anyway (saveLateLaunch) and
               the workflow terminates it. Open job already holding another instance -> this one is
               terminated at once.
  loop every 30 s:
    checkStep  refresh instance status and IP from Lambda, then decideCheck(job, instance, now)
               -> wait | terminate(status, reason). A check that fails (the database stayed down through its
               30 s retries) doesn't end the watch; the next poll tries again.
  terminateStep terminate the workflow's instance id first, before reading the database; then the saved id
               and anything live under instanceName (an instance that is already gone counts as terminated);
               then finishJob. A launch that was sent but that Lambda doesn't list yet ends the job without
               terminatedAt and with its clock at createdAt, so it keeps its GPU slot until the sweep looks.
               Lambda and database errors retried every 30 s for about 10 minutes.
  abandonStep  if terminateStep never got through: ends the job without terminatedAt (saving an instance
               only the workflow knew), so the sweep terminates it. Retried every 30 s for about 10 minutes.
               If both fail, both are tried again every minute for an hour.
  judging      only when terminate returned "succeeded" and the job has eval items: judgePlanStep, judgeStep
               4 at once, saveEvalSummaryStep (lib/train/judge.ts, see Judging). Never changes the status.
  scoring      in place of judging for a decide job (started with {jobId, mode: "decide"}), after every ending:
               scoreDecisionStep (lib/train/decide-steps.ts, see Decision models (decide mode)). No model call;
               never changes the status.
  publishing   after every ending: hubPlanStep with the final status, then for a judged glimmer-lora job whose
               adapter files are on the Hub (or the adapter job of a glimmer-publish job that succeeded):
               hubStoryStep, hubDatasetStep, hubModelStep, hubFinishStep (lib/train/hub-steps.ts, see Hugging Face
               Hub). Never throws and never changes the status; a step out of retries leaves the hub state "failed".
Instance (runner.py) -> POST /api/train/jobs/{id}/events with the job token:
  heartbeat (every 60 s), progress, log, artifact, eval (before done), serving (glimmer-serve only), done, failed
Instance (runner.py) -> GET /api/train/jobs/{id}/dataset?part=train|eval&page=N with the job token (see Datasets)
Instance (runner.py) -> POST /api/train/jobs/{id}/hub {plan | done} with the job token, before done (glimmer-lora and
  glimmer-publish): the upload plan, the bytes straight to the Hub's storage, the report (see Hugging Face Hub)
publishToHub workflow: the same publishing, started by an admin's Publish (POST /api/train/jobs/{id}/publish)
  "done" and "failed" set the final status at once and also ask Lambda to terminate right away (best effort),
```

`decideCheck` order: stop requested -> "stopped"; status already succeeded/failed by callback -> terminate with that status; instance terminated or preempted outside the platform -> "failed"; time limit -> "failed" ("Reached the N-minute limit"); dollar limit -> "failed"; no heartbeat 25 min after launch -> "failed"; no heartbeat for 10 min after the first -> "failed"; instance "unhealthy" -> "failed"; else wait.

The workflow loop also stops after `maxMinutes + 15` minutes no matter what, and then terminates.

`finishJob` decides the final status in the same SQL statement, from the row as it is then: a stop request makes it "stopped", a job that already ended keeps its own status (a done that landed while the caller was terminating wins), and only an open job takes the status the caller asked for. It keeps the first `terminatedAt`, and logs the termination once however many calls overlap.

### The sweep (lib/train/sweep.ts)

The backstop for a job whose workflow is gone (a database outage it couldn't ride out, `MAX_EVENTS_EXCEEDED`, a queue outage). It lists every live instance on the account but only ever touches the platform's: those named `mm-train-*`, and those a job claims by its saved instance id or the `muse-muse-job` tag (so a renamed instance is still found). Any other instance on the account is left alone.

- An `mm-train-*` instance that no job claims, an instance whose job ended, and a second instance for the same job: terminated.
- An open job's instance, in this order: an admin asked to stop (the job ends as "stopped"); past `maxMinutes + 10 min` or `maxUsd * 1.1`; then decideCheck's own rules with the limits left out (no heartbeat 25 min after launch, 10 min of silence, preempted or unhealthy). The job ends as "failed".
- Jobs stuck in queued or launching for 15 min are failed, with any instance under their name. A stuck launch that holds the launch claim but has no instance listed yet keeps its GPU slot (no `terminatedAt`, clock at `createdAt`) until a later sweep finds the instance or, 10 min after it ended, calls it gone.
- A launched job left open 30 min past its time limit is failed.
- An ended job with no `terminatedAt` whose instance isn't listed: a saved id is asked about with GET /instances/{id} first (the listing can lag); `terminatedAt` is stamped once it is gone. With no saved id, only 10 min after the job ended.
- An instance found running after its job was recorded as terminated (a launch Lambda listed late): terminated, and `extendTermination` moves `terminatedAt` to now and counts that time, so the job page and the daily cap include it.
- When GET /instances fails, instances whose ids jobs saved are still terminated by id: ended jobs without `terminatedAt`, and open jobs the rules above say to end. An instance no job saved waits for the listing.
- A run whose listing answered is noted (`recordSweepOk`, one `rate_limits` row a minute under `train-sweep-ok`), for the launch gate.

## Instance names and tags

- Name: `mm-train-<first 8 chars of job id>-<recipe>`, under 64 chars. Stored in `training_jobs.instance_name` when the row is created. Launch finds instances by this name; the sweep by this name, the saved instance id or the job tag.
- Tags: `muse-muse: train`, `muse-muse-job: <job id>`. The sweep uses the job tag only to find a job's instance, never as a reason to touch an instance no job claims.

## User data (lib/train/userdata.ts)

`buildUserData({ jobId, callbackBase, token, recipe, params, maxMinutes, deadlineEpoch?, cacheDir?, serveKey? })` returns a `#cloud-config` document:

- `write_files`:
  - `/opt/muse/job.json` (0600): `{ jobId, callbackBase, token, params, maxMinutes, recipe, deadlineEpoch }`, plus `cacheDir` (the cache filesystem's mount path) for a recipe with `usesCache`, and `serveKey` for a glimmer-serve job (see Live demo (glimmer-serve)). `deadlineEpoch` is the Unix second the runner must be done by: `launchStep` stamps it just before the launch request as `deadlineEpochFor(usableMinutes(...))`, so it is never after `launchedAt` plus the time the job's limits allow, and decideCheck never stops a job before it. Without one it defaults to now plus `maxMinutes`
  - `/opt/muse/runner.py` (0755): `RUNNER_PY` from `lib/train/recipes/runner.ts`
  - `/opt/muse/recipe.py` (0644): the recipe's script
- `runcmd`: start `python3 /opt/muse/runner.py /opt/muse/job.json` detached, logging to `/var/log/muse-job.log`.

`callbackBase` is `${env.platformUrl}/api/train/jobs/${jobId}`. Creating a job is refused when `env.platformUrl` isn't public (`publicHost` from `lib/sandbox/policy.ts` is null), since the instance couldn't reach a local platform. The document must stay under 1 MB and must not contain `LAMBDA_API_KEY` or any other env secret.

## Runner and recipes (lib/train/recipes)

Python files are kept as TypeScript string constants (`String.raw`), so Vercel bundles them with no file tracing. Never use `${` or backticks in the Python.

- `runner.ts` exports `RUNNER_PY`. It uses only the Python standard library. It reads job.json, starts a heartbeat thread (every 60 s), imports `recipe.py` and calls `run(ctx)`. It then posts `done` with the returned dict as metrics, or `failed` with the last 3 KB of the traceback. Callbacks retry 3 times with backoff and never print the token. `ctx` has:
  - `params`, `job_id`, `max_minutes`
  - `deadline`: the Unix time the job must be done by, job.json's `deadlineEpoch` (or `maxMinutes` from when the runner started, without one)
  - `log(text)`
  - `progress(step=None, total_steps=None, loss=None, message=None)`
  - `run(cmd, timeout=None, check=False, env=None, on_line=None, on_event=None, stall_seconds=None)`, which runs a shell command in `work_dir`, streams it to the log and posts its last lines as a log event. It reads the output in chunks rather than lines, so a progress bar's carriage-return redraws count as output, and keeps the text after a line's last carriage return. `env` adds variables for the command, and `on_line(line)` sees each output line as it arrives (its errors are logged, never raised). `on_event(line)` does the same for the lines the command writes to a pipe of its own, whose file descriptor is in its `MUSE_EVENT_FD`: a channel a progress bar on stderr can't write into. With `stall_seconds`, the command is watched: once it has written nothing on either for that long, the heartbeat thread posts one "Stalled: no output for N minutes from $ <cmd>" log and sends no more heartbeats until it writes again (the first one back says "No longer stalled"), so the platform's 10-minute silence rule ends a stuck job instead of it billing to its limit. The result is a `subprocess.CompletedProcess` with the last lines as `stdout` and `timed_out` set when the timeout killed it. With `check=True` a non-zero exit raises
  - `upload(path, name, kind)`, which asks `POST {callbackBase}/upload` for a Blob client token, PUTs the file to Vercel Blob and posts an `artifact` event. It returns None when the platform answers 503 (no storage). It declares the type `mimetypes` names when the platform takes it (`UPLOAD_TYPES`, the same list as `TRAIN_UPLOAD_TYPES` in `lib/train/types.ts`) and `application/octet-stream` otherwise. A grant covers one blob that can't be written twice, so when Blob refuses a retried PUT or multipart complete (the first try may have landed before its answer was lost) it asks for a fresh grant and uploads once more.
  - `work_dir`
  - `cache_dir`: the mounted cache filesystem (job.json's `cacheDir`) once it is a folder, waiting up to 60 s for the mount (`cacheWaitSeconds` in job.json for tests), or None (with a log line) when there is none
  - `get_json(path_and_query)`: GETs `callbackBase + path` with the job token, the same retries as callbacks (429 and 5xx, 3 times) and no redirects. A status of 300 or more raises `PlatformError` (with `.status`)
  - `dataset(part)`: pages `GET {callbackBase}/dataset?part=train|eval&page=N` from page 0 until `nextPage` is null and returns every item. A job with no dataset answers 404 and a dataset that isn't ready 409, which raise
  - `dataset_title`: the dataset's title from the pages `dataset()` read (None before that, or when a page has none)
  - `serve_key`: job.json's `serveKey` for a glimmer-serve job, else None. The runner blanks it out of every log line as `[serve key]`, as it does the token
  - `serving(port, cert_sha256, model, adapter_job_id)`: posts `{ type: "serving", port, certSha256, model, adapterJobId }` (the fingerprint lowercased, without colons) and returns True when the platform took it. Raises ValueError for a port or a fingerprint that isn't one, before sending
  - `eval(index, prompt, reference, base, tuned)`: posts `{ type: "eval", ... }` with each text field cut to 3,500 characters (and the longest shortened further if multibyte text would push the body past 15 KB). At most 60 per job; later calls only log and return False. Recipes send them before returning, so they land before "done"
- `smoke.ts` exports `SMOKE_PY`. It reads `nvidia-smi` (GPU name, memory), checks that torch sees CUDA and runs a matmul on the GPU, and reads free disk. It also checks HTTPS reachability of huggingface.co and pypi.org, and sends 3 progress ticks 20 s apart. It returns those as metrics. With `params.allowNoGpu` truthy it tolerates a missing GPU, which is how the local test runs it.

## Lambda client (lib/train/lambda.ts)

Base `https://cloud.lambda.ai/api/v1`, `Authorization: Bearer env.lambdaApiKey`, 20 s timeout per call, one retry on 429 or 5xx with a 2 s wait (a launch, a filesystem create or a firewall ruleset create retries only a 429). Errors throw `LambdaApiError(status, code, message)`. The key is never logged. Filesystems are only ever listed and created, never deleted (see Model cache). Firewall rulesets are only ever listed, created and patched, only the platform's own (by name), and never deleted (see Live demo (glimmer-serve)).

```ts
export async function listInstanceTypes(): Promise<LambdaInstanceType[]>              // GET /instance-types
export async function listInstances(): Promise<LambdaInstance[]>                      // GET /instances
export async function getInstance(id: string): Promise<LambdaInstance | null>         // GET /instances/{id}, null on 404

export async function launchInstance(input: { name: string; instanceType: string; region: string; userData: string; sshKeyName: string; tags: Array<{ key: string; value: string }>; fileSystemNames?: string[]; firewallRulesetIds?: string[] }): Promise<string> // POST /instance-operations/launch, returns the instance id; file_system_names and firewall_rulesets ([{ id }]) sent only when non-empty
export async function terminateInstances(ids: string[]): Promise<void>               // POST /instance-operations/terminate; a 404 or already-terminated is success

// listFilesystems, ensureFilesystem, findCacheFilesystem, cacheRegions, cacheFilesystemName: see Model cache
// listFirewallRulesets, ensureServeFirewall, serveFirewallName, serveFirewallRules: see Live demo (glimmer-serve)
```

`pickGpu` takes the asked type if it is one of the choices and has capacity; otherwise it takes the first choice with capacity in one of `preferRegions` (regions that already hold the model cache), then the first choice with capacity anywhere. Within a type, a preferred region comes first, then regions starting with `us-`. A type with no positive price is skipped. With `onlyRegion`, capacity in any other region doesn't count (a glimmer-serve job launches only where its adapter's cache is).

## Model cache (Lambda filesystems)

A recipe with `usesCache: true` (`glimmer-lora`, and `glimmer-serve`, which loads its adapter from there) keeps its Python venv and model weights on a Lambda persistent filesystem, one per region, so the next job in that region skips the install and the 21 GB download. Filesystems bill by stored GB per month even with no instance running (about 40 GB a region, roughly $8 a month at about $0.20 a GB, outside every job, daily and spend limit; `/fine-tuning` says so); the platform never deletes them (delete one by hand in the Lambda console when it is no longer wanted). Inside one, the recipe clears what dead jobs left and venvs nobody uses any more (see the cache layout below), but keeps every job's adapter.

- Name: `muse-muse-cache-<region>` (`cacheFilesystemName(region)`, prefix `CACHE_FILESYSTEM_PREFIX`). Mounted at Lambda's default `/lambda/nfs/<name>` (the filesystem's `mount_point`).
- Job creation: the jobs route calls `pickGpu(recipe.gpus, types, asked, recipe.usesCache ? await cacheRegions() : [])`; a `cacheRegions()` error only drops the preference, it never refuses the job. An asked GPU type with capacity still wins (in a cache region when it has capacity there); otherwise the first recipe GPU with capacity in a cache region is taken, then the first with capacity anywhere.
- Launch: `launchStep` calls `ensureFilesystem(job.region)` after the adopt and in-flight checks and before the launch claim, then launches with `file_system_names: [name]` and puts the mount path in job.json as `cacheDir`. If the filesystem can't be listed or created, the launch fails with a FatalError ("The model cache filesystem in <region> could not be found or created, so nothing was launched: ...") and nothing is claimed or launched. An adopted instance (found by name on a retry) is never asked about again. A glimmer-serve job instead calls `findCacheFilesystem(job.region)`, which only lists: a new, empty filesystem wouldn't hold its adapter, so a region with none fails the launch with a FatalError ("There is no model cache filesystem in <region>, so the adapter this job serves isn't there and nothing was launched.") before the claim.
- `ensureFilesystem` is idempotent and never loops on a create: it lists, and creates with one `POST /filesystems` `{ name, region }` only when the region has none (a 429 is retried once, since nothing was made). A `global/duplicate`, a timeout, a network error or a 5xx reads the listing once more and returns the filesystem if it is there; anything else (a quota refusal, say) is thrown. A cache name found in another region is refused (`filesystem-in-wrong-region`).
- On the instance, the runner waits up to 60 s for `cacheDir` to be a folder and sets `ctx.cache_dir` to it, or to None (with a log line) when it never shows up (see Runner and recipes). A recipe also checks it can write there (root squash would refuse) and otherwise runs without the cache.

```ts
export const CACHE_FILESYSTEM_PREFIX = "muse-muse-cache-"
export interface LambdaFilesystem { id: string; name: string; region: string; mountPoint: string; inUse: boolean; bytesUsed: number | null }
export function cacheFilesystemName(region: string): string
export async function listFilesystems(): Promise<LambdaFilesystem[]>          // GET /filesystems
export async function ensureFilesystem(region: string): Promise<LambdaFilesystem> // GET, then at most one POST /filesystems; launchStep only

export function pickGpu(choices, types, asked?, preferRegions?: string[])     // preferRegions: see "Job creation" above
// launchInstance input also takes fileSystemNames?: string[] (sent as file_system_names only when non-empty)
```

|---|---|
| `venvs/glimmer-<12 hex>/` | the uv venv; the hash covers the Python version, the uv version and every install line, so changing a pin makes a new one. Ready once `.muse-ready` is in it. Every job stamps the one it runs from (`.muse-last-used`); a venv of other pins with no stamp gets one when a job first sees it, and goes once no job stamped it for 12 hours (by then every job launched with its pins has ended, as long as `TRAIN_JOB_MAX_MINUTES` stays well under 12 hours). The one in use is never removed |
| `venvs/glimmer-<12 hex>.lock/` | the build lock (a folder, since `mkdir` is atomic on NFS), with an `owner` file; its holder touches it every minute, and one untouched for 10 minutes is broken |
| `venvs/glimmer-<12 hex>.building-<job>/`, `.stale-*` | a build in progress, and folders moved aside (a broken lock, a venv that wasn't ready, an old venv being deleted). Any job deletes those older than 12 hours, on a thread of its own |

## glimmer-lora recipe (lib/train/recipes/glimmer.ts)

A LoRA fine-tune of Muse Glimmer 30B on one dataset, then the dataset's held-out prompts answered by the base and the tuned model as eval items, for the platform to judge. It follows Unsloth's Muse Glimmer guide (unsloth.ai/docs/models/muse-glimmer and /train) and its Conversational Kaggle notebook (`Kaggle-Muse_Glimmer_(30B)-Conversational.ipynb`).

- GPUs, in order: `gpu_1x_h100_pcie`, `gpu_1x_h100_sxm5`, `gpu_1x_a100_sxm4`. `gpu_1x_gh200` is left out: it is arm64, and Unsloth documents arm64 only through a from-source Docker build (its DGX Spark Dockerfile), not the pip install below. Defaults: 150 minutes, $14, `usesCache: true`. These sit above the default ceilings (`TRAIN_JOB_MAX_MINUTES` 120, `TRAIN_JOB_MAX_USD` $5), so a job that asks for nothing gets 120 minutes and $5 until those are raised; with them raised (say 300 and $40), an admin can ask for more than the defaults.
- How long a run takes (`runEstimate` in `lib/train/logic.ts`): `maxSteps` at about 5 s a step on an H100 SXM5, 6 on an H100 PCIe and 12 on an A100 SXM4 (or any other GPU), plus 20 minutes in a region with the model cache or 45 without it. The jobs route refuses a run whose estimate is over `usableMinutes`, and the New job card shows the same estimate. A dry run has none.
- Params: `datasetId` (kind "dataset", required), `maxSteps` (default 120, 10 to 2000), `learningRate` (default 0.0002, 0.000001 to 0.01), `loraRank` (default 16, 4 to 128; `lora_alpha` is the same), `studentPrompt` (kind "text", "short" or "full", default "short"; the recipe refuses anything else when it starts), `dryRun` (0 or 1, default 0).
- Student prompt (distillation framing). The teacher, the dataset's writer (Muse Wonder for a dataset made now, Muse Spark 1.3 for one made before Oct 29, 2026), wrote every answer under the dataset's long task prompt (`datasetSystemPrompt(task)`, up to about 2,300 characters). With `studentPrompt` "short", every training conversation's system message is replaced by one line, "You are " and the dataset's title (`student_system`: "You are Muse Muse's brief writer." for a dataset named "Muse Muse's brief writer"; "You are a helpful assistant." when the title is missing, over 80 characters or only the start of the task, the name a dataset gets when it is made without one), and both the base and the tuned model answer the eval prompts under that same line. The references stay the teacher's answers. Neither model is told the task, so the scores measure what training taught: the base model has to guess the format, the tuned one learned it. With "full", training keeps the dataset's conversations as they are and both models answer under the system message they share (none when they differ), which measures how well each model follows the task's instructions; the base model often does well there without any training. The line used is in the first log line and in the metrics (`student_prompt`, `student_system`). `dryRun: 1` is also the cheap first check on a real GPU: it launches, mounts the cache, pages the dataset, sends the eval items (which get judged) and uploads a stand-in adapter, in a few minutes of GPU time.
- Install (once per region and pin set): uv 0.13.1 from its GitHub release, checked against `UV_SHA256` (a uv on PATH is never used), `uv venv --relocatable --python-preference only-managed --python 3.12`, then the notebook's install cell as `uv pip install` lines pinned to what it resolved to on 2026-10-27 for Python 3.12 on x86_64 Linux: `torch==2.11.0+cu128 torchvision==0.26.0+cu128 torchaudio==2.11.0+cu128 xformers==0.0.35 --index-url https://download.pytorch.org/whl/cu128`, `unsloth==2026.10.9 unsloth_zoo==2026.10.9 peft==0.21.2 accelerate==1.15.0 bitsandbytes==0.50.2 datasets==4.8.5`, `--no-deps torchao==0.18.0`, `transformers==5.15.0`, `--no-deps trl==0.22.2` (the last with `--compile-bytecode`, which compiles the whole venv). Only the direct packages are pinned, not a hash-locked set of every transitive one. Each step's timeout is its cap (15 minutes, 40 for an install) or less, so the job can still train after it; with under a minute to spare the job fails before installing. Then the readiness check imports what the child imports (Unsloth's `FastModel` and `train_on_responses_only`, torch, datasets, peft, bitsandbytes, transformers, trl), asserts `torch.cuda.is_available()` and must print `MUSE_CHECK transformers=5.15.0 trl=0.22.2`; only then is `.muse-ready` written.
- Two jobs and one venv: the build goes into `.building-<job>`, and one job builds at a time, holding the venv's `.lock` folder while the others poll every 15 s and reuse its venv when it is ready (a waiter gives up when too little time is left to train). The finished build is renamed into place, and the rename settles any race: it fails onto a folder that isn't empty, so the venv already there wins and the loser reuses it. A ready venv is never deleted or moved, since jobs may be running from it; a folder in its place that isn't ready is moved aside and left for the 12-hour cleanup. A failed build deletes its own folder, and only a lock's owner removes it. Jobs run the venv with `PYTHONDONTWRITEBYTECODE=1`, so nothing writes into it. When a reused venv makes the child fail with a `ModuleNotFoundError` before its imports are done, its marker is renamed to `.muse-broken` (nothing is deleted), so the next job builds it again.
- The runner imports recipe.py with the system python, so its top level is standard library only. The GPU work runs as `<venv>/bin/python -u recipe.py --child glimmer-config.json` through `ctx.run`, with `HF_HOME=<cache>/hf`, watched with `stall_seconds=1200` like every build step (20 minutes with no output is a stall). The child writes `MUSE_EVENT {...}` lines to the runner's event pipe (`MUSE_EVENT_FD`, falling back to stdout, where the recipe finds the prefix anywhere in a line in case a progress bar is glued in front), which the recipe turns into progress events (training every 10 steps with the loss, plus phase messages); results come back in `work/glimmer-result.json`, written aside and renamed so a killed child never leaves half of one.
- The deadline: the child gets until `ctx.deadline` less 5 minutes (the parent's own time, for the eval items and the upload) and is killed a minute after that. With under 15 minutes left for it, the job fails at once instead of loading a model it can't train.
- The child: `FastModel.from_pretrained(MODEL, revision=MODEL_REVISION, max_seq_length=2048)`, r30b's bnb-4bit build pinned to the hub commit `6f12bf52...` (The base model, above; jobs before Oct 31, 2026 loaded unsloth/Muse-Glimmer-30B-unsloth-bnb-4bit at `ecedda39...`); `FastModel.get_peft_model` with language, attention and MLP modules (vision frozen), `r = lora_alpha = loraRank`, dropout 0, bias "none", `use_gradient_checkpointing="unsloth"`, seed 3407. Text goes through the model's own ATEM chat template (`chat_template.jinja` in the model repo) with the leading `<|begin_of_text|>` removed and `reasoning_strength="low"`, which only sets the "Reasoning strength: low." line in the system block. The channels: an assistant message with `reasoning_content` renders as `<|start|>assistant to=self<|message|>` (reasoning), `<|eom|>`, then `<|start|>assistant to=user<|message|>` (the final answer) and `<|eot|>`; without it, only the final message. `<|eot|>` ends generation (it is in the model's `eos_token_id`), `<|eom|>` doesn't. The dataset's answers have no reasoning, so each training text ends `<|start|>assistant to=user<|message|>ANSWER<|eot|>` with no to=self message (`training_text`, which checks that every prompt follows `<|start|>user<|message|>` and every answer follows `<|start|>assistant to=user<|message|>` in the rendered text, so a template that renders otherwise fails the job before any answer). The template's generation prompt ends at `<|start|>assistant` and leaves the channel to the model, which opens its to=self reasoning; that choice is never trained, since it sits inside the response marker. So each eval prompt is the generation prompt with ` to=user<|message|>` appended (`eval_prompt`): it ends exactly as a training text does before its answer, and both models answer on the final channel at once, with no reasoning, the way the tuned one was trained. Base answers first (a fresh LoRA adds zero), greedy, `max_new_tokens=1024`, batches of 8, left padded; the answer is the text up to the first `<|eot|>`, `<|eom|>` or `<|end_of_text|>`. An answer that never closes (the budget ran out, or the model opened another message first) or is empty is sent as "[Unfinished: no complete final answer within 1024 new tokens. The raw output follows, with only the chat template's control tokens taken out.]" and the raw output with only the control tokens taken out, so the judge sees what the model wrote and that it never finished; `base_unfinished` and `tuned_unfinished` count them, and the summary says so when either is above 0. The base answers are written to the result file at once. Then `SFTTrainer` with the notebook's `SFTConfig` (batch 1, gradient accumulation 4, warmup 5, `max_steps=maxSteps`, `learning_rate`, `loss_type="nll"`, `adamw_8bit`, weight decay 0.001, linear schedule, `save_strategy="no"`) and `train_on_responses_only(instruction_part="<|start|>user<|message|>", response_part="<|start|>assistant to=user<|message|>")`. The child then checks the masks it made (`check_masking`): every training example must have trained tokens, and its first trained span must start with its answer (its first 40 characters, or all of it when `max_seq_length` cut it shorter); otherwise the job fails before training with which example and why (the marker wasn't found, or the span starts elsewhere). The job log gets, from the child's `log` events: the first training example's text with the trained span between `[train]` and `[/train]` and its trained-token count (sent before the check, so a failed check shows what was masked), and the first 600 characters of the base and the tuned model's raw output for eval item 0, control tokens kept. A trainer callback stops training early once the clock reaches the child's deadline less 1.3 times the base answers' time and 3 minutes, so the tuned answers and the save still fit; the summary then says "N of M steps (stopped early to finish within the time limit)". The adapter is saved with `save_pretrained` to `<cache>/models/<jobId>/` and the result file rewritten before the tuned answers, then the optimizer's memory is freed. A failure in the tuned answers is recorded as `tuned_error` and the child still exits 0.
- The recipe then sends one eval item per held-out prompt (a dataset holds out at most 100; the recipe and the runner stop at 120), uploads the adapter folder as `glimmer-lora-<job id start>.tar.gz` (kind "adapter") when storage is available and it is under 1 GB (a failed upload is logged, not fatal), and returns metrics: `train_loss_final`, `steps`, `max_steps`, `stopped_early` (yes or no), `train_seconds`, `base_answer_seconds`, `base_unfinished`, `tuned_unfinished`, `trained_tokens_min`, `trained_tokens_mean`, `max_new_tokens`, `peak_vram_gb`, `gpu`, `eval_items`, `train_examples`, `student_prompt`, `student_system`, `cached_weights` and `cached_venv` (yes or no), `cache_used`, `adapter_dir`, `adapter_uploaded`, `adapter_mb`, `adapter_url` when uploaded, and a summary. The parent reads whatever result the child left, whatever its exit: with no result the job fails with how the child ended and its last lines; with the base answers but no adapter it fails saying training didn't finish; with the adapter but no tuned answers it uploads the adapter, logs the metrics, sends no eval items (so nothing is judged) and then fails saying why.
- `dryRun: 1` skips the venv, the model and the GPU: it fetches the dataset, sends progress ticks, makes deterministic fake answers, writes a stand-in adapter folder, offers it for upload, sends the eval items and finishes. `lib/train/__tests__/runner.test.ts` runs it against the fake platform serving `/dataset` pages and checks the eval events.

## rl-grpo recipe (lib/train/recipes/rl.ts; TUNE_RL, off)

Reinforcement learning on a LoRA of r30b with TRL's `GRPOTrainer`. **It has never run on a GPU or against real TRL.** The code was written by reading trl 0.22.2's wheel source, and its tests use fakes. Its limits (90 minutes, $8) and its learning rate are guesses, with no estimate shown before launch.

- **Flag:** off, the recipe isn't in `offeredRecipes()` (the New job card, `GET /api/train/jobs`, the GPU list) and `launchJobRequest` answers 400. `recipeById` still finds it, so a job's page works after the flag goes off.
- **Python:** `glimmerHelpers()` plus its own code, like glimmer-serve, so it shares the venv pins, the cache and the pinned base. Only r30b: no base param, so TUNE_ANY_BASE doesn't apply. The child runs as `recipe.py --rl config.json`.
- **Task:** 2,000 training and 40 held-out arithmetic problems from a seed, never overlapping, with results computed from the numbers rather than by evaluating text. Prompts open the final channel with `eval_prompt`, and the model may work in short steps within 128 new tokens.
- **Reward (`score_answer`):** 1 for the right whole number in exactly one `<answer>` tag, 0.1 for a wrong number, 0 otherwise. No model grades anything.
- **Training:** 8 sampled answers a problem and 2 problems a step by default, logged every 5 steps. The tokenizer's eos is set to `<|eot|>`, since GRPO stops and masks at the tokenizer's eos only. Training stops early to leave time for the tuned pass.
- **Results:** done metrics, read by `lib/train/rl.ts` and shown by `components/train/RlResults.tsx` on the admin job page: `reward_curve` (at most 40 points), `heldout_*`, and up to 8 `example_N`, which always include answers that got worse when there are any. While it runs, the curve comes from `Mean reward N` progress messages. `rl-heldout.json` has every answer. A job with no tuned answers fails.
- **No judge, no Hub:** it sends no eval items, so `judgePlanStep` does nothing and no Meta call is made. Hub steps and the live demo only take glimmer-lora, so nothing is published or served, and there is no public result page. The adapter stays in the cache and goes up as an artifact.
- **Dry run:** `dryRun` 1 loads no model and reports made-up numbers, which the summary and the page both say.
- **Tests:** `lib/train/__tests__/rl.test.ts`, `components/train/__tests__/rl-results.test.tsx`.

## Datasets (lib/train/datasets.ts)

Training data Muse Wonder (`DATASET_MODEL`) writes from a task description; Muse Spark 1.3 wrote the datasets made before Oct 29, 2026. Table `training_datasets` (migration `drizzle/0003_training_datasets.sql`): `id, title, task, status ("generating" | "ready" | "failed"), requested, train (TrainExample[]), eval (EvalExample[]), train_count, eval_count, cost_usd, error, created_by, created_at, finished_at, workflow_run_id`, and `writer_model` (migration `drizzle/0008_lab_models.sql`: the model that writes it, saved when the route creates it; null means Muse Spark 1.3). Examples can run to megabytes, so only the paging and the generating steps read `train` and `eval`; every other query selects the head columns (`DatasetHead`).

```text
POST /api/train/datasets (admin)  -> refused while the platform's daily spend cap is reached (lib/quota spendPaused),
                                     then row "generating" with writer_model DATASET_MODEL, makeDataset started
makeDataset (one file: the workflow and its steps):
  loadDatasetStep      the task and the count; a dataset that isn't generating is left alone
  promptBatchStep      x ceil(count / 25) + up to 4 more: structured output {prompts}, 25 a batch, each batch leaning
                       to other styles (casual, detailed, beginner, expert, concrete specifics, a format, edge cases,
                       in a hurry): one each in turn when the count needs 8 batches or more, otherwise an even share
                       of the 8 per batch (stylesFor), so even a 20-example dataset has them all. The latest 40
                       prompts (cut to 140 chars) are shown as ones not to repeat. The workflow de-duplicates (case,
                       accents, spacing and punctuation folded) and stops at the count.
                       The batches that leaned to the same styles before are shown too, up to 40 more of their
                       prompts (avoidList), since those are the likeliest to come back as close variants.
                       Prompts over 1,500 chars are dropped. Under 16 different prompts fails the dataset. A later
                       batch that fails, once there are 16, ends the prompts and the answers go on with those (but
                       not when the spend cap is the cause).
  answerChunkStep      chunks of 12: 6 calls at a time, instructions datasetSystemPrompt(task) (answers under about
                       350 words), effort low, max_output_tokens 4000 (Muse Wonder bills its reasoning as output:
                       the answer, about 1,000 tokens at most, plus about 3,000 to reason), 90 s each with one SDK
                       retry, so a prompt takes at most about 3 minutes. An answer that failed, came back incomplete or empty, or is over 4,000
                       chars is skipped, not cut. Em dashes are taken out. Each call is charged (recordUsage and
                       cost_usd) as it returns, and each usable answer is saved at once into `eval` (stageAnswer; a
                       retried write saves it once). At the end of the step the chunk's answers move onto `train` as
                       {messages: [system, user, assistant]} in one statement (flushAnswers), so `train` is rewritten
                       once a chunk. A failed write after a paid call is tried again in the step about 5 times over
                       about 100 s. A retried step asks only the prompts with no saved answer, and one that finds the
                       dataset past its offset asks nothing. Past 120 s a step starts no new prompt and hands the
                       rest to the next step, so it ends in about 7 to 8 minutes at worst, under the 800 s limit. A
                       chunk with no usable answer is retried after 30 s only when nothing was billed (every call
                       failed); billed but unusable answers aren't asked again. Up to 2 such chunks are left out.
  finishDatasetStep    moves any answers still saved for a chunk onto `train`, counts what it holds, then in one
                       statement: the items evalSplit picks move to `eval` as {prompt, reference}, their
                       near-duplicates leave `train`, counts set, status "ready". Under 16 examples fails the dataset.
  failDatasetStep      on an error before answering starts: status "failed" with the error's first line.
```

- A dataset keeps what it paid for. Once answering has started, anything that stops it (the spend cap, the database, a third chunk Meta never answered) ends the answers, and finishDatasetStep makes the dataset "ready" with what it holds when that is at least 16, with a note in `error` ("Stopped early, once N of the M examples asked for were answered. <reason>"); with fewer it fails with the reason.
- Who writes: Muse Wonder by default. With `TRAIN_CONTRIBUTOR_WRITER=1` (or wherever `TEST_MODEL` is on), an admin may choose Spark 1.3 Contributor on the New dataset card, about 1/100th the output price, by confirming the task is made up: Meta's terms (6.2) bar sensitive, confidential or personal information on that tier and Meta may train on it. `writerFor` checks again at every step and falls back to Muse Wonder if it's off. Judging stays on Muse Wonder.
- Eval holds out 10% of the answered examples, at least 8 and at most 100, always leaving at least 8 to train on (`evalHoldoutCount`), near the evenly spread `evalIndexes` positions, so every batch's style is in it (`evalSplit`). Each position takes the closest prompt with no near-duplicate anywhere in the dataset: two prompts are near-duplicates when at least 70% of their words (after `promptKey`'s folding) are shared (`isNearDuplicate`, Jaccard). When none is left, it takes the closest prompt anyway and holds its near-duplicates out beside it while there is room; any still in train are dropped, never leaving fewer than 8 to train on. That catches reorderings, typos and a changed word or two, not a paraphrase in other words. The split is deterministic.
- Every training example's system message is `datasetSystemPrompt(task)`, the same instructions the answers were written with. Eval items carry only the prompt and the writer's answer as the reference. glimmer-lora answers them under a short system message made from the dataset's title (its `studentPrompt` "short", the default), or under the training examples' shared system message ("full"), so name a dataset as a role, such as "Muse Muse's brief writer".
- Every Meta call is recorded with `recordUsage({ source: "platform", endpoint: "responses" })` and added to `cost_usd`; a structured reply that never matched the schema is still recorded. Each model step checks `spendPaused()` first and stops the dataset ("The platform's daily spend cap is reached, so the dataset stopped.") once the cap is reached: before any answer that fails it, after that it keeps what it has (see above).
- A dataset whose workflow died stays "generating". No job can use it, and nothing bills for it. The admin pages call it "Stalled" after 6 hours.
- Measured on 2026-10-27 (the real steps against Muse Spark 1.3, locally): 20 examples took 24 s (one prompt batch in 7 s, 20 answers 6 at a time in 17 s) and cost $0.069, about $0.0035 an example; answers ran 1,100 to 1,300 characters. Muse Wonder hasn't been measured here: at Muse Wonder's prices ($4 in, $0.20 cached and $20 out per million) the same tokens cost about $0.016 an example, and a call takes 1.4 to 2 times as long. The New dataset card's estimate (`datasetCostRange`, `datasetMinutes`) uses Muse Wonder's prices, 350 to 450 input and 700 to 1,600 output tokens an example (Spark's count to more than twice it, since Muse Wonder's reasoning is billed as output), and 1.5 times the time it allowed for Muse Spark 1.3: 300 examples are about $4.62 to $10.14 and about 30 minutes.
- A job names its dataset with a recipe param of kind "dataset" (its key is `datasetId`). `validateParams` takes only a uuid there (lowercased); the jobs route then refuses with 400 a dataset that doesn't exist, is still generating or failed.

## Judging (lib/train/judge.ts)

A job whose recipe answers its dataset's held-out prompts with the base and the tuned model sends each as an eval callback before "done". Once the job has ended as "succeeded" and its instance has been terminated, Muse Wonder (`JUDGE_MODEL`) judges them and the job gets an eval summary. The judge is saved on the job (`training_jobs.judge_model`) as judging starts; a job judged before Oct 29, 2026 has none and was judged by Muse Spark 1.3.

Eval callbacks on `POST /api/train/jobs/{id}/events`:

- Body `{ type: "eval", index, prompt, reference, base, tuned }`: `index` a whole number from 0 to 9999, the four texts strings (the prompt not blank), each cut to 3,500 characters (`EVAL_TEXT_MAX`). Anything else is 400.
- An eval body may be up to 64 KB, since four 3,500-character texts can pass 16 KB once escaped or outside ASCII. Every other callback keeps the 16 KB limit.
- Like any callback, it counts as a sign of life and toward the 120 a minute, and is 409 `job_ended` once the job has ended.
- Logged as a training event of type "eval" by `recordEvalEvent`, which locks the job row, so callbacks at once can't pass the cap: at most 60 per job (`EVALS_MAX`), then 409 `eval_limit` with `{ max }`. An item sent again with an index the job already has is a retry: 204, and it isn't logged twice.

Judging, at the end of `trainJob` (lib/train/workflow.ts):

```text
terminate returned "succeeded" ->
  judgePlanStep          the job's eval indexes (at most 120) and its dataset's task. Nothing when it has none or already
                         has a summary; nothing when MODEL_API_KEY isn't set or the spend cap is reached, and then an
                         unjudged summary with a note ("Judging skipped: ...") and a log line; otherwise
                         judge_model JUDGE_MODEL on the job, then the log line "Muse Wonder is judging N eval items."
  judgeStep x n, 4 at once   Muse Wonder (JUDGE_MODEL), structured output, effort low; usage recorded, then a
                         "judgement" event
  saveEvalSummaryStep    eval_summary on training_jobs and a log line; with nothing judged, an unjudged summary with a
                         note ("Judging failed: none of the N eval items could be judged.") and a log line
```

- Judging starts only after `terminate` returned, so it never keeps a GPU billing, and nothing in it can change the job's status: a judge step that fails is left out of the summary, and an error in judging as a whole is swallowed.
- The judge sees the user message, the reference, and the two answers blind as A and B: the base model's is A on even indexes and B on odd ones, so neither labels nor position favor one model. It returns `{ note, scoreA, scoreB, better: "A" | "B" | "tie" }`; scores are clamped to whole numbers from 1 to 10 and the note is cut to 30 words. The verdict is logged as `{ type: "judgement", index, baseScore, tunedScore, better: "base" | "tuned" | "tie", note }`. When the scores differ, `better` follows them; when they are equal the judge's own pick stands.
- `judgeStep` is safe to run again: an item that already has a judgement is returned as it is, at no cost, without asking Meta. Usage is recorded (`source "platform"`, endpoint `responses`) before the judgement is logged. A reply that never matched the schema is recorded and not retried.
- `EvalSummary` (`training_jobs.eval_summary`, `TrainJobView.evalSummary`): `items, tunedWins, baseWins, ties, avgBaseScore, avgTunedScore` (hundredths) and `judgeCostUsd`, the sum of what the judge steps cost (an item judged again after a crash counts at 0). An unjudged summary (`unjudgedSummary(note)`, typed `UnjudgedSummary` in logic.ts) has 0 items and a `note` saying why; `unjudgedNote(summary)` reads it back. The job page takes judging's outcome only from this, never from log text.

```ts

unjudgedSummary(note), unjudgedNote(summary)
// store.ts
recordEvalEvent(jobId, body, max?) -> "recorded" | "duplicate" | "limit", listEvalIndexes(jobId), getEvalItem(jobId, index),
```

## Decision models (decide mode)

A glimmer-lora job with `mode: "decide"` trains a decision model instead of a chat adapter: a small LoRA adapter on Muse Glimmer 30B, trained on a person's labeled examples, that picks one of their labels (or "None of the listed options matches") for each input, with a probability for each read from the model's first answer token. It is scored by the platform with no judge and no Meta call. The design, the format, every number's definition and what is still to check are in `docs/DECISION_MODELS.md`; this section is how decide mode sits in the lab. **Nothing of it has run on a real GPU yet:** the GPU side ran only on fake Unsloth and torch, and the first real run waits for the owner's approval (D8 there).

```text
admin, New decision dataset card -> POST /api/train/datasets {kind: "decision", title?, question, labels, rows | csv | jsonl}
  -> checked and split at once (no model, no spend, no workflow): 201 {dataset, report}, status "ready"
admin, New job card in Decide mode -> POST /api/train/jobs {recipe: "glimmer-lora", params: {datasetId, mode: "decide", epochs?, scoreOnly?}}
  -> the mode must match the dataset's kind, publish is 0, the run estimate counts renderings and scored prompts,
     and trainJob starts with {jobId, mode: "decide"}
GPU (GLIMMER_PY decide_run) -> GET .../dataset?part=train|dev|eval (50 renderings a page, decideJson on each page)
  -> base scores on dev and test, training, the adapter and decide.json saved, tuned scores on the same prompts
  -> POST .../events {type: "decide", part, items} (100 items a callback, 8,000 a job) before done or failed
trainJob, after terminate (or abandon), whatever the ending: scoreDecisionStep in place of judging -> eval_summary
  (a DecisionSummary) and one log line; publishing's plan step then skips the job (hubJobProblem)
admin, Start a live demo -> a glimmer-serve job on the decision adapter -> the GPU serves POST /decide, not /generate
browser -> POST /api/lab/{id}/decide {state} -> both models' picks, each with its own T
product -> POST {GATEWAY_URL}/decide (the muse-decide permission) -> a decision, or the stand-in for a build token
```

### Datasets of kind "decision"

- Migration `drizzle/0017_decision_datasets.sql` adds three columns to `training_datasets`: `kind` (text, "chat" by default), `decision` (the `DecisionSpec`: question, labels, seed, split and per-label counts, source) and `decision_rows` (`{train, dev, test}`, each row `{input, label}`). `train` and `eval` stay empty, so no reader of chat datasets changes, and the head reads leave out `decision_rows`. 0017's snapshot chains to 0015's because 0016 (another branch's) hasn't landed: whichever lands second is rechained at merge (`docs/DECISION_MODELS.md`, "Migration").
- `POST /api/train/datasets` with `kind: "decision"` (`lib/train/decision-datasets.ts`, `checkDecisionUpload`): a question of 5 to 300 characters, 2 to 12 labels (names 1 to 60 characters, unique ignoring case, never the `none` text; descriptions up to 200), and rows as JSON, CSV (`input,label`, RFC 4180) or JSONL, each input 1 to 3,000 characters and its label given by name or id. At least 20 rows a label and at most 3,000 in all, the body under 4 MB. Rows whose inputs fold to the same text are merged; one input with two labels is dropped and listed. 201 `{dataset, report}`, or 400 `{error, problems: [{line, message}]}` with every problem at once (20 at most). It needs neither `MODEL_API_KEY` nor room under the spend cap: nothing is generated or spent and no workflow starts. Any other `kind` than "chat" or "decision" is a 400. A chat body keeps its 16 KB limit.
- The split is made once, deterministic and seeded: per label, test 20% (at least 5), dev 10% (at least 3, used only to fit T) and train the rest (at least 12). Near-duplicates (70% shared words, chained, across labels too) go to one split together, so no test row has a near-twin in train or dev. Checking and splitting 3,000 rows with 12 labels took 0.64 s on the owner's laptop.
- `writer_model` is "person" ("public" for Muse Decide's mix), named "The person who uploaded it" (`lib/train/models.ts`). `GET /api/train/datasets/{id}` adds `sampleRows`, the first 5 train rows of each label, for admins. The Lab reads select `kind` and the spec without its seed, never a row.

### The job

- Params (`lib/train/recipes/index.ts`, `validateParams`): `mode` ("chat" or "decide"; unset means chat, so a chat job's params are exactly as before), `epochs` (decide only, 1 to 4, default 2), `scoreOnly` (decide only, 0 or 1: base Glimmer scored, nothing trained, no adapter). `maxSteps` and `studentPrompt` are chat only. `publish` is 0 in decide mode, and 1 is refused on the platform and again on the GPU.
- The jobs route refuses decide mode on a chat dataset and chat mode on a decision dataset (`datasetModeProblem`), and checks the run with `runEstimate(recipe, params, gpu, cached, decideRunSize(spec, params))`: training renderings at 4, 6 or 7 a second (A100 SXM4, H100 PCIe, H100 SXM5) and scored prompts at 4, 6 or 8 a second, twice (once for `scoreOnly`), plus the usual 20 or 45 minutes. Those rates are estimates until a real run measures them.
- The dataset route, for a decision dataset: `part=train`, `dev` or `eval` (test), 50 renderings a page (`DECIDE_PAGE_SIZE`; the worst page measured 3.1 MB), `{kind: "decision", items, nextPage, total, title, decideJson}`. Train items are `TrainExample` rows whose answer is one letter; dev and test items carry no answer. Only a job in decide mode (its own params, or its adapter job's for a serve job) reads one: any other gets 409 `not_decide_mode`. Its cap is the job's own page count plus 120 an hour. `part=dev` on a chat dataset is a 400.
- On the GPU (`GLIMMER_PY`, see `docs/DECISION_MODELS.md`, "The GPU side"): chat mode is untouched; decide mode scores dev and test with base Glimmer (8 prompts a pass, the first token's log-probabilities over the whole vocabulary in float32), trains at 16 renderings a step with 2 accumulated and `group_by_length` for `min(2000, ceil(renderings / 32))` steps, saves the adapter and `decide.json` beside it (`<cache>/models/<jobId>/`), then scores the same prompts with the tuned model. A rendering over 2,048 tokens is dropped and counted, never cut. Every score is sent before anything else can fail, so a failed run still gives base Glimmer's numbers.
- The events route takes `{type: "decide", part: "dev" | "test", items}` only from a glimmer-lora job in decide mode: 1 to 100 items a callback, each `{index, base, baseMass, tuned, tunedMass}`, at most 64 KB, logged once per index (`recordDecideEvent`), 409 `decide_limit` past 8,000 items a job.

### Scoring instead of judging

`scoreDecisionStep` (`lib/train/decide-steps.ts`) runs after a decide job's terminate (or abandon), whatever its ending, and never changes its status. It reads the job's "decide" events and its dataset's dev and test rows, lays them out as the dataset route served them, and saves `summarizeDecisions`' result as `eval_summary` (a `DecisionSummary`, `kind: "decision"`) with one log line, such as "Scored all 48 held-out examples, with no judge and nothing spent: the tuned model was right on 41 (85%), base Glimmer on 32 (67%). ... It can be wrong: check anything that matters." The numbers: accuracy with a Wilson 95% interval, macro F1, per-label precision, recall and F1, the confusion matrix, the `none` and decline rates, T fit on dev only (with 20 or more scored dev rows; otherwise 1 and "not calibrated"), calibration error before and with T, reliability bins, letter mass, and two baselines (the commonest label and a word-overlap rule) on the same rows. When it can't score, it saves an unjudged summary whose note says why. `judgeModelOf` names no judge for a decision summary. A chat job's judging is unchanged.

## Live demo (glimmer-serve)

"Try tuned Glimmer live". The `glimmer-serve` recipe serves ONE trained glimmer-lora adapter on one GPU for a set number of minutes. While it runs, that adapter's public result page (`/fine-tuning/{trainJobId}`) has a Try it live box: anyone types an app idea and gets the base and the tuned Muse Glimmer's answers side by side, from the same GPU (the base with PEFT's `disable_adapter`). It is a job like every other, with the same lifecycle, limits, sweep, deadline and termination: its `run(ctx)` keeps a server up until its minutes are up or `ctx.deadline` less 3 minutes, then returns, and the runner posts done.

```text
admin: Start a live demo (the adapter's page) or the New job card
  -> POST /api/train/jobs { recipe: "glimmer-serve", params: { adapterJobId, minutes } }
     adapter servable (adapterProblem), one open demo per adapter (409 demo_running), GPU only in the adapter's region
     (pickGpu onlyRegion), limits minutes + 15 (recipeDefaults), refused when they can't cover that (serveFitProblem)
launchStep: findCacheFilesystem(region) (the cache already there, never a new one), ensureServeFirewall(region),
     then the token, serveKey = serveKeyFor(jobId, hashToken(token)) into job.json, launch with the cache mounted and
     firewall_rulesets [{ id }]
GPU, run(ctx): the adapter at <cache>/models/<adapterJobId>/, the system line from the adapter's dataset, ensure_venv,
     then the child: a self-signed certificate (openssl), the 4-bit base and the adapter, HTTPS on 8443
  -> "serving" { port, certSha256, model, adapterJobId } -> training_jobs.serve_endpoint { ip (Lambda's), port,
     certSha256, startedAt }
browser -> POST /api/lab/{trainJobId}/try { prompt } -> rate limits and the demo's one slot -> HTTPS pinned to certSha256,
     POST /generate with "Authorization: Bearer <serveKey>" -> { base, tuned, ms }
end: its minutes after it came up, or ctx.deadline - 180 s when that is first -> the server drains and stops -> done
     -> terminated like every job (no eval items, so nothing is judged)
```

### Recipe, params and limits

- Params: `adapterJobId` (kind "adapter", required) and `minutes` (number, default 30, 10 to 120: how long it serves once the model is loaded). `validateParams` takes only a uuid for the adapter, lowercased. The jobs route stores `minutes` whole (`serveMinutes`, rounded down), and the GPU reads it the same way (`read_serve_params`: floor, then clamp), so the limits, the page's end time, the proxy's cutoff and the server all count the same minutes.
- An adapter can be served (`adapterProblem` in `lib/train/logic.ts`, the jobs route's 400) when its job is glimmer-lora, succeeded, wasn't a dry run (`dryRun` under 1), and its latest done metrics say `cache_used` "yes" with `adapter_dir` ending in `models/<its id>`, so it is at `<cache>/models/<id>/` on the filesystem of its own region (`training_jobs.region`). It must also have trained on r30b (`isSparkOpenDerivative`): serve and quantize jobs load r30b's weights, and a LoRA from plain Glimmer has the same shapes, so it would load without error and answer as a model nobody evaluated. Only glimmer-publish (`opts.uploadOnly`), which loads no base, still takes an adapter from before the switch. `listAdapterOptions` lists those, newest first, for the select; `getAdapterSource(jobId)` reads one with its done metrics.
- GPUs: glimmer-lora's (`gpu_1x_h100_pcie`, `gpu_1x_h100_sxm5`, `gpu_1x_a100_sxm4`), picked only in the adapter's region: `pickGpu(recipe.gpus, types, asked, [region], region)`. `usesCache: true`.
- Limits: `recipeDefaults(recipe, params)` fills in what the admin didn't ask for: the minutes plus `SERVE_BOOT_MINUTES` (15, to boot, mount the cache and load the model), and dollars for one minute more at `SERVE_SIZING_CENTS_PER_HOUR` ($4.29 an hour, an H100 SXM5, the priciest it may get), rounded up to the cent. 30 minutes gives 45 minutes and $3.29; the recipe's own `defaultMaxMinutes` and `defaultMaxUsd` are those. The ceilings cap them as for every job (`clampLimits`). With the default $5 ceiling a 60-minute demo needs 75 minutes but $5 allows 69 on an H100 SXM5, so the route refuses it there (`serveFitProblem`) and it fits on an A100 SXM4 or an H100 PCIe; the Start a live demo control warns about it.
- One open demo per adapter (409 `demo_running`). Two asked for at the same moment can both pass that check, so right after `createJob` the route asks `earlierOpenServeJob(adapterJobId, jobId)` (an open serve job of that adapter whose `(created_at, id)` is before the new row's own, in SQL, so a tie still has one winner); when there is one, the new job is marked failed ("Another live demo of this adapter started at the same moment, so this one was not launched.") and the reply is the same 409, so one demo always survives. `TRAIN_MAX_ACTIVE` still allows one GPU at a time, so a demo can't start while a job trains. A demo counts toward the daily cap at its full dollar limit like any job.

### Serving key, TLS pinning and what the browser sees

- The serving key is `serveKeyFor(jobId, tokenHash)` in `lib/train/serve.ts`: hex HMAC-SHA256 with `GATEWAY_TOKEN_PEPPER` of `serve:<jobId>:<tokenHash>`. The platform stores only the token's hash, so the key is never in the database: launchStep puts it in job.json as `serveKey` next to the job token (and blanks it out of launch errors as `[serving key]`), and the proxy derives it again from the job's row on each call. The runner blanks it out of every log line as `[serve key]`.
- The demo server answers only `Authorization: Bearer <serveKey>`, on every route.
- TLS: the child makes a new self-signed certificate with the openssl CLI at start (RSA 2048, 2 days, CN `localhost`, which says nothing about what serves it), and `certSha256` is the SHA-256 of its DER bytes in lowercase hex. The proxy connects with Node's `tls.connect` and `rejectUnauthorized: false` (no CA validation), compares the peer certificate's `fingerprint256` with the stored one in constant time (`certFingerprint` takes either form), and only then writes the HTTP request on that connection, so a server with another certificate never gets the key or the prompt (`pin_mismatch`). Fingerprint pinning is the only check.
- The address: a serving callback carries only the port and the fingerprint. `applyCallback` writes `serve_endpoint.ip` from `training_jobs.instance_ip`, the IP Lambda reports, and `setInstanceIp` keeps it in step when Lambda reports a new one, so a leaked job token can't point the proxy anywhere else. A later serving callback replaces the endpoint (a restarted server has a new certificate).
- The browser never gets the IP, the port, the key, the fingerprint or the serve job's id. The store's `getLiveDemo` (`LiveDemoView`: serve job id, state, minutes, endsAt) is mapped to `PublicLiveDemo` (state, minutes, endsAt) by `toPublicLiveDemo` in `components/train/results.ts` before the public page renders, and the proxy's replies are only answers or error codes. `TrainJobView.serving` (admin) is `{ startedAt, endsAt }`. The admin event log shows the serving callback with only the first 12 characters of the fingerprint.

### Firewall ruleset

- `ensureServeFirewall(region)` in `lib/train/lambda.ts` returns the ruleset `muse-muse-serve-<region>` (`serveFirewallName`), whose one rule (`serveFirewallRules`) lets in TCP 8443 from `0.0.0.0/0`. Nothing else: Lambda's spec says the global ruleset (`GET /firewall-rulesets/global`) holds "Firewall rules that apply across all regions", so SSH on a demo's GPU stays exactly as the owner set it there (narrowed to their own address, say), and the platform never opens port 22 to everyone. Port 8443 is open to every address because the proxy runs on Vercel, whose outbound addresses aren't fixed; the serving key, the pinned certificate and the server's per-connection deadline are what protect it.
- Idempotent like `ensureFilesystem`: it lists (`GET /firewall-rulesets`) and reuses a ruleset of that name in that region as it is while it lets 8443 in from everywhere, whatever else the owner added to it. When it no longer does (someone edited it in the console), one `PATCH /firewall-rulesets/{id}` sends its own rules with the 8443 rule appended, so the owner's other rules stay. Only a region with none gets one `POST /firewall-rulesets { name, region, rules }` (a 429 retried once). A duplicate, a 409, a timeout, a network error or a 5xx reads the listing once more and returns the ruleset when it is there; anything else is thrown. Never deleted: delete one by hand in the Lambda console when it is no longer wanted.
- launchStep calls it for glimmer-serve jobs only, after `findCacheFilesystem` and before the launch claim (a failure is a FatalError: "The live demo's firewall ruleset in <region> could not be found or created, so nothing was launched: ..."), and launches with `firewall_rulesets: [{ id }]`. Every other recipe launches without one and keeps Lambda's defaults. An adopted instance is never asked about again.

### The GPU side (lib/train/recipes/serve.ts)

- `SERVE_PY` is its own docstring, then glimmer-lora's Python as it is (`glimmerHelpers`: `GLIMMER_PY` without its docstring and its `__main__` block, which throws if `GLIMMER_PY` no longer has that shape), then the serve code. So the venv (and its build lock), the cache, the pinned model and revision, the chat template, `eval_prompt`, `final_answer` and the event relay are exactly training's. `glimmer.ts` is unchanged.
- `run(ctx)` fails before any GPU work when `adapterJobId` isn't a uuid, job.json has no `serveKey`, the cache isn't mounted or writable, `<cache>/models/<adapterJobId>/adapter_config.json` is missing (the adapter isn't in this region), it is a dry run's stand-in, there are no adapter weights, or fewer than 10 minutes are left to serve before `ctx.deadline` less 3 minutes (5 minutes, checked again once the venv is ready).
- The system line: `GET /dataset?part=train&page=0` (the dataset route pages a glimmer-serve job its adapter job's dataset), then `student_system(title, shared system)`, the line glimmer-lora's short student prompt trains with: "You are " and the dataset's title as a role, such as "You are the Muse Muse brief writer.", or "You are a helpful assistant." for a missing, long or task-start title. When the platform answers with an error status (the dataset is gone or not ready), both models answer under "You are a helpful assistant." and the log says so. An adapter trained with `studentPrompt` "full" still gets the short line. The line is in the job log and in the metrics (`system`).
- The child runs as `<venv>/bin/python -u recipe.py --serve serve-config.json` through `ctx.run`, like glimmer-lora's, with `HF_HOME=<cache>/hf` and `stall_seconds=1200`. Its config (with the key) is written 0600 and removed when it exits. It makes the certificate first, so a missing openssl fails in seconds, then `FastModel.from_pretrained(MODEL, revision=MODEL_REVISION, max_seq_length=...)` (8,192 for a chat adapter, for products' chat; a decision model's 2,048, as training), `PeftModel.from_pretrained(model, <cache>/models/<adapterJobId>, is_trainable=False)` and `FastModel.for_inference` (a failure there is logged and it answers without it).
- Each prompt is answered as glimmer-lora's eval answered its held-out prompts: `eval_prompt` (the template at low reasoning, under the system line, with the final channel opened), greedy, `max_new_tokens=400` (`SERVE_MAX_NEW_TOKENS`), the base model first inside `model.disable_adapter()`, then the tuned one. Both together get `SERVE_ANSWER_SECONDS` (100, equal to the constant in `lib/train/recipes/serve.ts`, and a test checks it plus the proxy's 10 s to connect fits its 120 s wait): the base `max_time` half of it (transformers' `MaxTimeCriteria`), the tuned what is left, and the tuned isn't started with under 5 s left (`TUNED_MIN_SECONDS`). So the GPU never keeps the lock answering a prompt the proxy gave up on. The answer is `final_answer`'s text; one that never closes, or that the clock stopped or never started, is "[Unfinished: no complete answer within 400 new tokens or the time limit. ...]" and the raw output with only the template's control tokens taken out.
- A visitor's prompt goes into the template as text, and the tokenizer reads special-token strings in text as real tokens, so `neutral_prompt` neutralizes them first, on the GPU: every `<|` becomes `< |` (every Glimmer template token starts with it, and `< |` can't make a new one), and any other special or added token the tokenizer has (`all_special_tokens`, `added_tokens_encoder`) is dropped, again until none is left, since dropping one can join the halves of another. A prompt can't close its user turn, forge a system message or open the assistant's answer.
- The server: HTTPS on `0.0.0.0:8443` (`SERVE_PORT`), TLS 1.2 or later, a thread per connection with the TLS handshake on that thread, at most 64 connections at once and 4 from one address (`MAX_CONNECTIONS`, `MAX_CONNECTIONS_PER_IP`; more are closed at once, before any handshake), and a 30 s socket timeout on each read or write. A connection must finish its handshake and send a whole request with the key within 10 s of being accepted (`REQUEST_DEADLINE_SECONDS`), or a `RequestDeadline` timer shuts it (the plain socket's shutdown, so a read blocked on it returns at once), however slowly it trickles bytes: a socket timeout starts again with every read, this doesn't. It is cancelled once the key checks out, so a slow answer is never cut off. So a stranger can hold a slot for 10 s at most, and four from one address, and can't lock the platform's proxy out. It reads a request's body before any reply, sends no Server header, and logs nothing about who asked or what.
  - `POST /generate { prompt }` -> 200 `{ base, tuned, ms }`, the prompt trimmed and cut to 600 characters (`PROMPT_MAX_CHARS`). One at a time (a lock): 409 `busy` while another is answered. 400 `bad_json` or `no_prompt`, 411 without a Content-Length, 413 over 16 KB, 503 `stopping` once its time is up, 500 `generation_failed` (logged; the server goes on, but 3 in a row, `FAILS_TO_STOP`, as a broken CUDA context gives, stop it at once with a note, "The demo server stopped after 3 live answers in a row failed (last: <error type>)", which fails the job, so the GPU doesn't bill for minutes nobody can use; an answer that works starts the count again).
  - `GET /health` -> `{ ok, busy, model, adapterJobId, served }`.
  - `POST /v1/chat/completions` (a chat adapter's server only; a decision model's answers 404): products' chat in OpenAI's chat shape, below.
  - 401 `unauthorized` without the key, on every route; 404 for any other path.
- Once it listens, the child emits "serving" and the recipe posts `ctx.serving(port, certSha256, model, adapterJobId)`. When the platform doesn't take it, it is sent again with each "alive" event, 5 times in all, then the server stops (nobody could reach it) and the job fails. The child writes an "alive" event every minute, so the 20-minute stall watch never holds back the heartbeats while it waits for prompts; each answer becomes a progress message ("Serving live: N answered").
- It stops at whichever comes first, `ctx.deadline` less 180 s (`SERVE_MARGIN_SECONDS`, equal to `SERVE_STOP_MARGIN_SECONDS` in logic.ts) or its minutes after it started serving: the listener closes, an answer in progress gets up to 150 s to finish (`DRAIN_SECONDS`, the longest answer's budget, a chat answer's 135 s, and 15 s), and the child writes its result (`peak_vram_gb` null when torch.cuda itself fails) and exits. `run(ctx)` returns `adapter_job_id`, `served`, `busy_refused`, `unauthorized`, `bad_requests`, `errors`, `serve_minutes`, `load_seconds`, `max_new_tokens`, `system`, `gpu`, `peak_vram_gb`, `cached_weights`, `cached_venv` and a summary. A child that ends before serving fails the job with its last lines (and, from a reused venv with a `ModuleNotFoundError` before its imports, marks that venv broken as glimmer-lora does); one that ends while serving fails it with how many it answered.

### The platform side

- Events route: a `serving` callback is taken only from a glimmer-serve job (else 400), with `port` 8443 and `certSha256` a SHA-256 fingerprint (64 hex characters, or the colon form, stored lowercased); `model` and `adapterJobId` are cut to 200 characters. It counts as a sign of life and toward the 120 a minute, moves the job to running, writes `serve_endpoint` and is logged.
- `serve_endpoint` (jsonb, `ServeEndpoint`): `{ ip, port, certSha256, startedAt }`, `ip` null until Lambda reported one.
- `serveEndsAt(job)`: when serving is expected to stop, its minutes after `startedAt`, or launch plus `usableMinutes` less `SERVE_STOP_MARGIN_SECONDS` when that comes first (only the latter before it serves; null before launch). `toLiveDemoView(row, now)`: null once the job ended, a stop was asked for or `endsAt` passed; "live" when it is running with a usable endpoint (an IP, port 8443, a fingerprint, `usableEndpoint`); "starting" otherwise.
- `getLiveDemo(adapterJobId, now)` and `liveServeTarget(adapterJobId, now)` read the newest open serve job for the adapter (`params.adapterJobId`, not ended, no stop asked for). `liveServeTarget` (proxy only) returns `{ jobId, tokenHash, ip, port, certSha256 }` for a live one with a token.
- `POST /api/lab/{trainJobId}/try`, in order: 403 `cross_site` for a request from another site (`isCrossSite`, the same check signed-in writes use); 404 `no_live_demo` for an id that isn't a uuid; the body (JSON, at most 8 KB) and the prompt, trimmed, 1 to 600 characters (400 with a sentence); 404 `no_live_demo` when the job has no public result page (`getResultJob`: not judged yet) and the caller isn't an admin (`requireUser`, which confirms the flag against the database), the same reply as no demo, before any rate limit, so the access matches what Start a live demo says (only admins can try an unjudged job's demo); 404 `no_live_demo` when `liveServeTarget` finds none; 5 prompts per client IP (`x-real-ip`) in a fixed 10-minute window, key `lab-try:ip:<ip>` (429 `rate_limited`, `scope` "ip", `retryAfterSeconds`), counted before the slot, so a busy reply uses one of them; the demo's one slot (`takeDemoSlot`, key `lab-try-busy:<serve job id>` in `rate_limits`, 3-minute windows that also count the previous one, so a slot a crashed call never gave back clears within 6 minutes; 409 `busy`), given back in a `finally`; 60 prompts per demo per clock hour, key `lab-try:demo:<serve job id>`, counted only for prompts that got the slot (429, `scope` "demo"); then `askLive` with 120 s (`serveTiming.answerMs`). The GPU's 409, 423 or 429 is 409 `busy`; its 503 (time's up) is 404 `no_live_demo`; its 400, 413 or 422 is a 400 sentence; a timeout is 504 `timeout`; a pin mismatch, no connection, another error status or an answer that isn't `{ base, tuned, ms }` (or is over 256 KB) is 502 `demo_unavailable`. Each answer is cut to 8,000 characters; replies are `cache-control: no-store`. `maxDuration` is 150 s. Failures are logged with the serve job id and the error code, with the GPU's address blanked out.

### Products' chat (lib/train/glimmer-serving.ts)

Products answer with hosted Muse Glimmer through wave 3's gateway, in demo windows only (unit 11 owns the windows, the
gateway route, the daily cap and the Muse Wonder fallback). General's side is the serve job's chat route and the backend
the gateway calls. `lib/train/glimmer-serving.ts` is the single source of the settings; the Python has the same numbers,
and `runner.test.ts` keeps them equal.

- Meta's guidance (`content/meta-docs/pages/muse-glimmer/deploy.md`): sample with temperature 1.0, top_p 0.95 and top_k 64,
  all three on every request, never greedy (lines 239 and 243, `GLIMMER_SAMPLING`); stop on `eos_token_id` [200001, 200008],
  `<|end_of_text|>` and `<|eot|>` (line 317, and lines 1015 to 1025 for Transformers, `GLIMMER_EOS_IDS`; the GPU checks its
  tokenizer agrees, or the route is off); never stop on `<|eom|>` (lines 319 to 321): it is taken out of any stop a caller
  asks for and never added for base Glimmer or a trainChannel 1 adapter. The eval and `/generate` stay greedy.
- The channel. An adapter trained before trainChannel (trainChannel 0, every adapter so far) answers on the final channel
  the prompt opens (`eval_prompt`, as it was trained) and also stops at `<|eom|>` and `<|start|>`, server side only (the
  trainChannel stop rule: they catch it drifting into a second message and can't cut reasoning, since none follows a
  prefilled final channel). Base Glimmer and a trainChannel 1 adapter answer from the template's generation prompt and
  reason first; the answer is their last final-channel message, and one cut off mid-thought is empty with finish "length"
  (line 690). New tokens: 1,024 by default final-only, 4,096 reasoning, never more than 4,096. A chat server loads the
  model with an 8,192-token context (prompts up to 4,096 tokens, 422 `too_long` past it); a decision model's keeps 2,048.
- trainChannel reaches the GPU in the serve job's params: `launchJob` writes the adapter's (`trainChannelOf`, 0 when it has
  none) as it does for a glimmer-quantize job, and no caller may send it.
- `POST /v1/chat/completions { model, messages, max_tokens?, stop?, temperature?, top_p?, top_k? }` -> 200 `{ id, object:
  "chat.completion", created, model, choices: [{ index, message: { role, content }, finish_reason }], usage: { prompt_tokens,
  completion_tokens, total_tokens }, ms }`. `model` is `muse-glimmer` for base Glimmer (the adapter off) or the adapter's job
  id for the tuned model. Messages: 1 to 64, system only first, the last a user message with text, 32,000 characters in
  all; every content is neutralized as `/generate`'s prompt is. The tuned model answers under the adapter's training line
  when the messages have no system message. Sampling sent must be Meta's (400 `bad_sampling`). One request at a time,
  through the same lock as `/generate` (409 `busy`), within `CHAT_ANSWER_SECONDS` (135). 400 `bad_json`, `unknown_model`,
  `bad_messages`, `bad_max_tokens`, `bad_stop` or `stream_unsupported`, 413 `too_large` (or over 256 KB), 422 `too_long`,
  503 `stopping` (also with less than `CHAT_ANSWER_SECONDS` left before the window ends, so the drain at shutdown never
  cuts a chat answer off), 501 `chat_unavailable` (the route couldn't be set up; the log says why and `/generate` still serves), 500
  `generation_failed`.
- The platform: `askChat` in `lib/train/serve.ts` (pinned TLS and the serving key, as `askLive`; `serveTiming.chatMs`

- The contract unit 11 imports: `serveJobChatBackend(adapterJobId, now)` returns a `GlimmerChatBackend` (or null when no

  unreachable), mapped by `glimmerErrorReply`: busy 409, stopping 503 `glimmer_closed`, timeout 504,
  bad_prompt 400 `bad_request` (the caller's to fix), unreachable, pin_mismatch, refused and bad_answer 502. No error
  names the GPU's address. `stop` is an optional field added beside the contract's.
- Tests: `lib/train/__tests__/glimmer-serving.test.ts` (the settings, the backend on fake windows, `askChat` against a

### Not proven yet

Nothing here has run on a GPU or on Lambda. ## Hugging Face Hub

When a glimmer-lora job succeeds and is judged, the platform publishes it to the Hugging Face Hub: a model repo with the LoRA adapter and a model card that leads with why it was made, and a dataset repo with the training data and a dataset card. Both are made private, committed, read back and checked, then made public when `HF_PUBLIC` asks for it (the default). The HF token never leaves the platform: the GPU hashes the adapter's files, asks the platform for presigned upload URLs, and sends the bytes straight to the Hub's storage with no Hub credential; the platform makes the commit once the job is judged. An adapter that exists only on a Lambda model cache (one trained before publishing existed, or one whose upload failed) is uploaded by a short `glimmer-publish` job that mounts that cache in the adapter's region and does only the upload part. Research notes on the protocol and the cards: `docs/HF_EXPORT_RESEARCH.md`.

```text
glimmer-lora GPU, after the eval items and the adapter archive (ctx.hub_upload in lib/train/recipes/runner.ts):
  POST /hub {action: "plan", files, small} -> the platform makes <ns>/muse-glimmer-30b-<slug>-lora-<job8> private,
       asks preupload about every file, keeps the small ones it marks "regular" on the job, asks the LFS batch
       (basic, multipart, never xet) about the rest -> {repo, uploads}; hub state "uploading" (a plan replaces the one before)
  the bytes -> the presigned storage URLs, with no credential (a multipart file part by part, then its completion)
  POST /hub {action: "done", uploaded, failed} -> hub state "uploaded", or "failed" with the reason
trainJob, after terminate and judging (lib/train/workflow.ts publish), every step under the run's claim:
  hubPlanStep     takes the claim: hub state "publishing" with a claim id, once. Off, not eligible or not uploaded: says why
  hubStoryStep    "Why this exists": Muse Wonder (STORY_MODEL, saved as storyModel), or the template's story
  hubDatasetStep  <ns>/muse-muse-<slug>-<dataset8>, private if new: data/train.jsonl, data/eval.jsonl; read back
  hubModelStep    each LFS object asked of the LFS batch again, then one commit: the objects by oid, the small files
                  (adapter_config.json normalized), README.md, LICENSE, muse_muse_run.json; read back
  hubFinishStep   HF_PUBLIC on: model public, then the dataset card, then dataset public (put back on a failure);
                  off: private. The visibility read back; hub state "published" with the links
admin Publish (POST /api/train/jobs/{id}/publish {why?}):
  every file on the Hub -> the publishToHub workflow: the same steps
  otherwise             -> the model repo made on the Hub (a refusal costs no GPU), then a glimmer-publish job through
                           POST /api/train/jobs (in the adapter's region, its cache mounted, on the cheapest free GPU
                           there), whose GPU plans and uploads for the adapter job; once it succeeds, its own trainJob
                           publishes the adapter job
```

### Three repos per run

A judged adapter can have a third repo, its local files: `<ns>/muse-glimmer-30b-<slug>-gguf-<first 8 characters of the adapter job's id>`, next to its `-lora-` repo, made by a glimmer-quantize job and published by that job's own trainJob (see Local files (glimmer-quantize)). What changed on this path for it:

- **The GPU's calls.** A glimmer-quantize job acts for itself. The names and the size cap are per recipe (`hubNameProblem` and `hubMaxBytes` in `lib/train/hub-cards.ts`, `hub_name_ok` and `hub_max_bytes` in runner.py): glimmer-lora and glimmer-publish keep the adapter's names and 10 GB. A glimmer-quantize job sends only its builds, `muse-glimmer-30b-<its slug>-<level>.gguf` for the levels its params name, up to 32 GB each (`HUB_GGUF_FILE_MAX_BYTES`, 413 `too_large` past it), and `system`, `params` and `tuned.jinja` (`HUB_GGUF_SMALL_NAMES`). Those three come whole in `small` and are checked byte for byte before anything uploads (`ggufSmallProblem`): `system` must be the adapter's `student_system`, a blank line and "Reasoning strength: low."; `params` Ollama's for the job's `trainChannel`; `tuned.jinja` exactly the tuned template, required for an adapter trained before `trainChannel`. A plan whose small files fail these checks is skipped and saved "failed" with why; one without a file it needs, or without a build, is skipped. The BF16 conversion, the Q8_0 reference and anything else stay on the GPU.
- **One file at a time.** An answer whose part URLs would pass 3.5 MB (`PLAN_ANSWER_MAX`) isn't sent. With more than one file in it, the answer is 413 `plan_too_large` with `perFile: true`, and runner.py plans again for each file alone with `only: [path]` (that answer's uploads are only that file's, while the plan the job keeps is still the whole folder), then reports once at the end. One file whose own parts pass it gets 413 with its `path` and `parts`, and that file fails: one file's parts can't be paged yet. `only` must name files of the plan (400 otherwise).
- **Digests back.** `ctx.hub_upload` returns each sent file's sha256 (`sha256` in its result), so glimmer-quantize records its builds' digests without reading 50 GB again.
- **The workflow.** `hubPlanStep` gives a glimmer-quantize job's plan the kind "gguf" (`claimGguf`: off; busy; files that never all reached the Hub, "failed" with `GGUF_NOT_UPLOADED` in `lib/train/hub-steps.ts`; an adapter that isn't published, "waiting"; else "publishing" under a claim), and `publish` in `lib/train/workflow.ts` runs `hubGgufStep` and `hubGgufFinishStep` in place of the story, dataset, model and finish steps. A glimmer-quantize job that ends without succeeding fails an upload it left unfinished.
- **The adapter's card.** Once a GGUF repo of it is published, its "How to use it" adds "To run it on your own computer, in LM Studio, llama.cpp or Ollama, take <repo>". A public card names only a public GGUF repo (`ggufLinkOf`). `hubGgufFinishStep` commits that card alone (README.md, only when it changed); publishing the adapter again writes the same card. `hubFinishStep` decides the pointer again once the model repo's visibility is set, and commits the README again when it differs from the one `hubModelStep` wrote (`cardGguf` in the hub state): a GGUF repo published while the adapter itself was publishing, which found the adapter busy and left its pointer to that run, or `HF_PUBLIC` changed between the steps. An adapter whose publishing ends private takes every published GGUF repo of it private too, and their hub states say so (`hideGguf`): the repos hold the merged weights.
- **Publish on a glimmer-quantize job** (`POST .../publish`): 409 `not_publishable` with the reason (`ggufJobProblem`, or `GGUF_NOT_UPLOADED`), 503 `hub_off`, 409 `publishing`, else 202 and the publishToHub workflow. It never starts an upload job: the files were only on the job's GPU.

| Setting | What |
|---|---|
| `HF_TOKEN` | A token that can write repos under `HF_NAMESPACE` (a fine-grained one with write access to the namespace's repos; per-repo scopes can't cover repos that don't exist yet). Secret: see Secrets and trust |
| `HF_NAMESPACE` | The user or organization the repos are made under |
| `HF_PUBLIC` | Unset, empty, "1", "true", "yes" or "on" (any case): the repos are made public once verified (the default). "0", "false", "no", "off" and anything else keep them private, and then the public pages show no links |
| `HF_ENDPOINT` | `https://huggingface.co` by default. https only, since every call carries the token; plain http only on localhost, for the tests' fake Hub. The cards always link to `https://huggingface.co` |

`env.hubOffReason` is null when publishing can run, otherwise a plain reason: "HF_TOKEN isn't set", "HF_NAMESPACE isn't set", "HF_NAMESPACE isn't a Hugging Face user or organization name" or "HF_ENDPOINT isn't an https origin (plain http only on localhost)". It only says which setting is missing, never a value. Until the token exists, every plan answers a skip, the job's hub state says "off" with that reason, and nothing else changes: the run, its judging and its pages are exactly as before. Nothing publishes a job judged while publishing was off once it is turned on: Publish on the job's page does (for one whose files never went up, such as run 2, job 83d71f74, through a glimmer-publish job in us-east-1), and the card shows such a job as not published, with Publish, rather than the old "off".

### Which jobs publish

- A glimmer-lora job that succeeded, wasn't a dry run, had its GPU shut down and was judged (an eval summary with items, the same rule as its public lab page), unless its `publish` param is 0. An admin's Publish publishes a job whose `publish` is 0 too.
- Its GPU uploads during the run (glimmer-lora's `publish_adapter`, after the eval items), so the commit only waits for judging. A job whose files aren't all on the Hub when it is judged waits ("The adapter's files aren't on Hugging Face yet. Publish uploads them from the model cache with a short GPU job, then publishes."): the workflow never starts a GPU on its own.
- A glimmer-lora job in decide mode never publishes, by the run or by Publish: `hubJobProblem` refuses it first, and an unset `publish` reads as 0 there (see Decision models (decide mode)). Its card, `decisionCard`, waits for adapter-only publishing.
- A job published before can be published again (Publish again on its page, say with a new why): the steps commit only what differs from what the repos have.
- The `why` an admin writes leads the card's "Why this exists": the glimmer-lora `why` param when the job starts, or the textarea of the job's Hugging Face card, saved by `POST .../publish` when it differs from the why the card would print now (`effectiveWhy` in `lib/train/logic.ts`: the one saved with Publish, else the param). An empty one is saved as "" and clears it, the param's too. A changed why has the story written again around it; pressing Publish with the why the card already has pays for no new story.

### The GPU's calls (POST /api/train/jobs/{id}/hub)

The job token, exactly as for the events route. `{id}` is the caller's own job. A glimmer-lora job acts for itself; a glimmer-publish job acts for the glimmer-lora job its `adapterJobId` param names, and its token can act for no other: the target is never taken from the body.

- `{ action: "plan", files: [{ path, size, sha256, sample }], small: { path: base64 } }`. `files` names every file of the adapter's folder, `sample` the base64 of its first 512 bytes (`HUB_SAMPLE_BYTES`). `small` carries the small ones whole (each at most 1 MB, 3 MB in all: `HUB_SMALL_FILE_MAX_BYTES`, `HUB_SMALL_TOTAL_MAX_BYTES`); every small file must be one `files` names, with its size and sha256 (400 otherwise). At most 100 files and 100 small files (`HUB_FILES_MAX`), each file at most 10 GB (`HUB_FILE_MAX_BYTES`), the body at most 4.4 MB.
- Only these names are published, each in the folder's root (`HUB_FILE_NAMES`, the same list as runner.py's `HUB_NAMES`): `adapter_model.safetensors`, `adapter_config.json`, and the tokenizer's and processor's files (`tokenizer.json`, `tokenizer.model`, `tokenizer_config.json`, `special_tokens_map.json`, `added_tokens.json`, `vocab.json`, `merges.txt`, `chat_template.jinja`, `chat_template.json`, `preprocessor_config.json`, `processor_config.json`, `video_preprocessor_config.json`). Any other file (a checkpoint folder, `optimizer.pt`, `training_args.bin`, PEFT's `README.md`, a full model's `config.json` or weights, a case variant of a name) gets no upload and stays out of the commit.
- The configs the platform reads (`HUB_CHECKED_NAMES`: `adapter_config.json` and the tokenizer's and processor's JSON configs) must come whole in `small`; one sent only as a file to upload is left out, since the platform can't read it. Each must be a JSON object with no `auto_map` (which points a loader at code from another repo), and `adapter_config.json` must name the recipe's base model (`unsloth/Muse-Glimmer-30B-unsloth-bnb-4bit`) and a 40-character `revision` or none. A config that fails is a skip, saved on the job as "failed" with the reason ("The adapter isn't published: ..."). The platform commits `adapter_config.json` as a normalized copy: the base model and the revision the card states (the recipe's when it had none), its top-level keys sorted, a 2-space indent.
- The answer is 200 `{ skip }` with a plain reason when publishing is off (saved on the job as "off"), the caller ended, it is a dry run, `publish` is 0, the job is published or being published, a glimmer-publish target can't be published (`hubJobProblem`), the folder has no `adapter_model.safetensors` or no `adapter_config.json` in `small`, or a checked config fails. Otherwise the platform makes the model repo private (a 409 that it exists is fine, a conflicting operation is tried again), asks preupload about every file, and keeps on the job the small files it marks "regular", to commit itself. Every other file, small or not, gets an upload from the LFS batch, asked for `["basic", "multipart"]` only: `{ path, oid, size, transfer: "none" }` (the Hub has it), `"basic"` with `{ href, header }`, or `"multipart"` with `{ chunkSize, parts: [{ partNumber, url }], completionUrl }`. The answer is `cache-control: no-store`.
- A plan replaces the one before (`withPlan`): runner.py sends the whole plan every time, so the job's state never holds more than one plan's caps, whatever a GPU sends. The oids the Hub already has, and those an earlier report of the same GPU gave that are still in the plan, count as uploaded. A plan from another job's GPU (a new glimmer-publish job) starts the uploaded list over. A plan that would land on a job a run is publishing, or one that is published, answers 409 `busy`.
- The URLs are credentials while they last: they go only to the GPU in this answer, and are never stored or logged. A verify action's Authorization header in the batch answer never reaches the GPU. A 403 from one means it expired: the runner sends the whole plan again, once per file, and takes the fresh URLs for that file and for every file it hasn't sent yet.
- The runner starts no transfer within 2 minutes of its deadline, and cuts off one still sending 1 minute before it (`HUB_ABORT_SECONDS`), so one slow upload can't push a trained job past its time limit, where it would fail and never be judged.
- `{ action: "done", uploaded: [{ path, oid, size }], failed: [{ path, error }] }` -> 204. Only from a job that hasn't ended (409 `ended`: its token works for 15 minutes more), about its own plan (409 `no_plan`), while that plan is "uploading" (409 `not_uploading`): so a late or stray report can't undo "published" or hand out a second publishing claim. Each uploaded object must be one of the plan's. Its oid joins the uploaded list; a failure fails the upload with the GPU's reason, any signed URL in it blanked out; with every file of the plan in, the hub state is "uploaded".
- 60 calls an hour per job (`train-hub:<job id>` in `rate_limits`), then 429. A Hub that is down, rate limiting or busy (a timeout, a network error, a 5xx, a 429, a conflicting operation) is 502 `hub_unavailable`, which the runner tries again. A refusal (any other 4xx, such as a token that can't write repos under `HF_NAMESPACE`) is 409 `hub_refused`, not tried again, and saved on the job as "failed" with the reason (and "Check that HF_TOKEN can write repos under HF_NAMESPACE." after a 401 or 403), so the job page says why before anyone pays for a retry. The runner logs both with the Hub's reason.

### Names

- Model: `<ns>/muse-glimmer-30b-<dataset slug>-lora-<first 8 characters of the job id>`. Dataset, one per dataset and shared by every job trained on it: `<ns>/muse-muse-<dataset slug>-<first 8 characters of the dataset id>`.
- The slug is the dataset's title, apostrophes and a leading "Muse Muse" dropped, through `slugify` (lowercase letters, digits and single dashes, at most 40 characters, cut at a word), or "dataset". Every name passes the Hub's rules (`validRepoName`: 1 to 96 of `[A-Za-z0-9._-]`, no leading or trailing `-` or `.`, no `--` or `..`, no `.git` at the end). "Muse Muse's brief writer" and job 83d71f74 give `muse-glimmer-30b-brief-writer-lora-83d71f74` and `muse-muse-brief-writer-17c76f2c`.

### The hub state (training_jobs.hub)

`HubState` in `lib/train/types.ts`: `status` (off, waiting, uploading, uploaded, publishing, published, failed), `reason`, `modelRepo`, `datasetRepo`, `modelUrl`, `datasetUrl`, `public`, `files` (the LFS manifest: path, size, sha256), `small` (base64), `uploaded` (oids), `uploaderJobId`, `publishJobId`, `uploadStartingAt`, `claim`, `modelCommit`, `datasetCommit`, `why`, `story`, `storyBy`, `storyModel` (the model that wrote a "spark" story; none means Muse Spark 1.3), `storyCostUsd`, `publishedAt`, `updatedAt`. The rules are pure functions in `lib/train/hub-cards.ts` (`withPlan`, `withDone`, `hubUploaded`, `hubJobProblem`) and `lib/train/logic.ts` (`hubBusy`, `effectiveWhy`, `toHubView`).

- `updateHub(jobId, change)` in the store writes it: `change` gets the state as it is and the job's row, and the write lands only while the state is still the one it saw (`is not distinct from` in one update), worked out again from a fresh read otherwise, 5 times at most. So two writers never undo each other and the publishing claim is taken once. It never touches the job's status.
- The claim: `hubPlanStep` sets "publishing" with a random `claim` id, and every later step of that run gets the id and stops (a FatalError, writing nothing) once the state no longer holds it. A "publishing" state more than 30 minutes old (`HUB_PUBLISHING_STALE_MS`) was left by a workflow that died, and Publish may claim it again; the old run, if it was only slow, is then fenced off, and its fail step can't fail the new one. Finishing or failing clears the claim.
- `uploadStartingAt`: Publish's own claim while it starts a glimmer-publish job, taken only by the press that still sees the same upload job (3 minutes at most), so two presses at once start one GPU; the other answers 409 `upload_running`.
- A glimmer-publish job that ends without succeeding fails its adapter job's upload ("The upload job ... ended as failed before the adapter's files were all on Hugging Face. Publish tries again."), when that job still waited on it.
- The admin page gets `HubView` (`toHubView`, `TrainJobView.hub`): the status, reason, repos, links, the why the card prints, who wrote the story, whether it is public, whether a "publishing" state is stale (`stale`, so the card offers Retry), and how many of the planned files the Hub has. Never the small files, the claim, the story's cost or an upload URL, which is never stored. The Lab reads select `hubLinks` only (the status and the two links, in SQL, only once published and public), so nothing else of the state reaches the public pages. `listJobs` and the sweep's reads select the state without `small` (`jobListColumns`, `hub - 'small'` in SQL); only `getJob`, which publishing reads, has it.

### Publishing (lib/train/hub-steps.ts)

- Each commit leaves out what the repo already has (the tree's git oid for a regular file, its LFS oid for an LFS one), asks preupload about the rest, uploads a platform file it marks "lfs" through the LFS bridge itself (a dataset JSONL over 10 MB, say), commits in one NDJSON call, then reads the tree back and checks every path, size and oid (`verifyFiles`). A step that runs again commits nothing twice, and publishing again with nothing new commits nothing.
- The dataset repo, in `hubDatasetStep`: `data/train.jsonl` (the training examples as trained on, `{"messages": [system, user, assistant]}`) and `data/eval.jsonl` (the held-out items in the same format, with the task's system message and the reference as the assistant's answer, so both splits load as one config). They are the dataset's own and the same for every job trained on it, em dashes and all, so committing them to a repo another job made public shows nothing new. Its card waits for `hubFinishStep`.
- The model repo, in `hubModelStep`: a repo that is public although the job was never published, or while `HF_PUBLIC` asks for private, is made private first. Every object of the plan is asked of the LFS batch again: the Hub answers no upload for an object it stores (as git-lfs reads it; no verify URL is guessed), so one it answers an upload for isn't there, comes off the uploaded list and fails the publishing ("Hugging Face doesn't have ... Publish uploads it again."), and Publish starts a glimmer-publish job. Then one commit: the objects by oid (`lfsFile`; the Hub adds them to `.gitattributes`), the small files (each checked config read again, `adapter_config.json` as its normalized copy), `README.md`, `LICENSE` (fetched from `<HF_ENDPOINT>/meta-models/Muse-Glimmer-30B/raw/main/LICENSE`, refused unless it is the Apache License) and `muse_muse_run.json`. A name outside `HUB_FILE_NAMES` is never committed.
- `hubFinishStep` writes the dataset card and sets both repos' visibility, then reads it back from the Hub (`GET /api/models/<id>`, `/api/datasets/<id>`): `public` is true only when both are public. With `HF_PUBLIC` on: the model repo public first, then the dataset card, then the dataset repo public, so a public dataset card never names a private model; when a part fails, each repo this run made public is made private again (a failed undo is logged), so a failure leaves both as they were. With it asking for private: the model repo private; with no other public model on the dataset, the dataset repo goes private too and gets this job's card, and with others it stays as it is, with its card first rewritten as the newest of theirs, so it never names this private model.
- A Hub that is down or rate limiting, after the client's own retries, is retried by the step after a minute; a refusal is fatal, with "Check that HF_TOKEN can write repos under HF_NAMESPACE." after a 401 or 403. A step out of retries fails the publishing with its reason (`hubFailStep`, under the run's claim). Steps log a line each to the job's event log ("Hugging Face card: ...", "Published to Hugging Face: <model> and <dataset>.").

### Any Meta base (TUNE_ANY_BASE, off; lib/train/bases.ts, lib/train/base-check.ts)

Admins may train on another Meta model, from Advanced on the plan or the full job form. Off, every job is what it was on r30b, and a base in a request is refused. Meta's models only: Llama 3.1, 3.2, 3.3 and 4, and Muse Glimmer builds, from meta-llama, unsloth or OfflineBase. Everything else, LFM included, is refused by name before the Hub is asked, and again on the id the Hub answers with.

- **Checks**, each time at the picker, Start and launch (`resolveBase`): allowlist, a commit pinned to 40 hex, architecture (`LlamaForCausalLM`, `Llama4ForConditionalGeneration`, `MuseGlimmerForConditionalGeneration`), license, safetensors size against GPU memory (4-bit files times 1.18, from Unsloth's 71 GB for Scout's 60.4 GB files). 16-bit repos over 65 GB are refused. Only what the check returned is written to the job's params, and no caller can send those params. The recipe checks their shape again (`use_base`).
- **Gated repos:** a HEAD with HF_TOKEN; 401 or 403 refuses with a sentence to accept the license and check the token. HF_TOKEN never reaches the GPU: the job asks POST `/api/train/jobs/{id}/base-files` for short-lived links, and each large file is checked against its sha256.
- **Templates:** each family has its own markers in the recipe's `FAMILIES`, read from its `chat_template.jinja`. Llama 3 loads with `FastLanguageModel` and explicit target modules, as Unsloth's notebooks do; Llama 4 with `FastModel` and no vision layers. `use_exact_model_name=True` is always on for a picked base, because Unsloth otherwise swaps a repo for its mirror and drops the pinned revision.
- **Never run on a GPU:** every Llama path. r30b and the original Glimmer are the only bases that have run here, and the plan says so. Cost and time scale r30b's measured step by parameters, at least half, plus the download.
- **Licenses:** `licenseDuties` next to `isSparkOpenDerivative`. A Llama model says "Built with Llama", has a Hub name starting with `Llama-`, and its repo ships the version's LICENSE and USE_POLICY.md read from Meta's repo with HF_TOKEN; if they can't be read, the publish fails rather than ship without them. Meta-written datasets are allowed on these bases.
- **Off with a reason:** decide mode is 4-bit Glimmer builds only, and serving and local files (GGUF) refuse anything not trained on r30b, since their merge base and checks are that model's.

### Auto upload (TUNE_AUTO_PUBLISH, lib/train/tune/auto-publish.ts)

Off by default. With it on, an admin's tune run launches with publish 1, so it goes through the same Hub path as any publishing job once it succeeds and is judged. Advanced turns it off per run. The signed plan keeps `publish: 0`, so plan hashes don't change: Start keeps the choice in rate_limits, with no row meaning off, and launchForRun checks it again.

- Never: visitors, dry runs, decision models, a dataset a product owns, a run for a product, or a task that quotes a person's own rows (`taskHoldsPersonRows`, which `ownerRowsProblem` now refuses for manual Publish too, old datasets included).
- Visibility: an auto-uploaded run stays private unless HF_PUBLIC is set to public. Unset means private here, and still means public for a manual Publish.
- A dataset Spark 1.3 Contributor wrote (`keepDatasetPrivate`): the model follows HF_PUBLIC, the dataset repo stays private, the model card names the writer and doesn't link the repo, and its GGUF card leaves it out.
- A failed upload shows its reason on HubCard, with Publish to retry. With under 8 minutes left the GPU skips its upload and the job waits for Publish: nothing starts a GPU by itself.

### The Hub client (lib/train/hub.ts)

Over fetch, on `HF_ENDPOINT`: `createRepo` (`visibility: "private"`, a 409 for an existing repo is fine, one for a conflicting operation is tried again), `preupload`, `lfsBatch` (transfers `["basic", "multipart"]`; an object the Hub stores comes back "none", which is also how publishing checks an upload), `uploadLfs` (the platform's own uploads, with no credential), `commit` (NDJSON: a header line, then `file` and `lfsFile` lines), `setVisibility` (`PUT .../settings {visibility}`), `repoVisibility` (`GET /api/models/<id>` or `/api/datasets/<id>`, its `private`), `listFiles` (the tree, following its pages), `verifyFiles`, `whoami`, `fetchPublicText`. Each call times out after 30 s (an upload after 15 minutes) and is tried again up to 3 times after a 429, a 5xx, a timeout or a network error, waiting 1, 2, then 4 s (or Retry-After, at most 30 s); a 4xx is never tried again. Errors are `HubApiError(status, code, message)` with the token blanked out as `[HF token]` and anything that looks like a signed URL as `[signed URL]` (`redact`). The token is read on each call, so a new one takes effect at once.

### The cards (lib/train/hub-cards.ts)

Every number in a card comes from the records (the job, its done metrics, its eval summary and items, its dataset) or from the glimmer-lora recipe's own source, never from a model. No em dash appears in a card: every text put in one (the task, the why, the story, the answers, the notes, the system message) goes through `noEmDashes`, and the Python's `SYSTEM` string writes one as `\u2014`, so the string stays the one training used. Model-written text in a card's prose (the judge's note) has its Markdown and HTML escaped, so it shows as written and can't add a link, an image or a heading; the answers are in fences. The cards link to `https://huggingface.co` (`HUB_SITE`), whatever `HF_ENDPOINT` is.

- The model card's front matter is the shape the Hub's validator took (docs/HF_EXPORT_RESEARCH.md): `base_model: <the base the job recorded>` (r30b's bnb-4bit build since the switch), `base_model_relation: adapter`, `library_name: peft`, `pipeline_tag: text-generation`, `license: apache-2.0` (for a Derivative of Muse Spark Open, `license: other` with `license_name: apache-2.0-and-muse-model-license` and `license_link: MUSE_MODEL_LICENSE.md`, the tag `built-with-muse-spark-open`, and Built with Muse Spark Open with the Usage Policy's points under the title: see The base model), `language: [en]` only when the dataset's title and task are plain ASCII, tags, `datasets: [<dataset repo>]`, and `model-index` with the judge's win rate and both average scores, its source the job's public lab page. Its sections, in order: Why this exists (the admin's why, the story, then the card's own sentence with the dataset's counts and the eval's result, `resultText`); What it does (the task, and the system message in a fence); Results (the blind eval table: wins, average scores, unfinished answers, ties, win rate, judging cost, the blind A/B order, and one held-out example with both answers and the verdict, saying which of A and B the base model's answer was, in fences that show them as they are); How it was trained (the base model at its pinned revision, QLoRA with Unsloth and TRL, rank, alpha, dropout, learning rate and schedule, steps, batch, examples, max sequence length, the student system message (one line for the short prompt; for the full one, its length, since What it does shows it), the GPU, its minutes and cost, the final loss); How to use it (transformers with `AutoModelForMultimodalLM` and PEFT, and Unsloth as the live demo loads it, both rendering the prompt exactly as training and eval did: the chat template at reasoning strength "low", the bos token taken off, the final channel " to=user<|message|>" opened, greedy, 1,024 new tokens, the answer cut at the first `<|eot|>`, `<|eom|>` or `<|end_of_text|>`); Data; Limits; License (Apache 2.0 from the base, its LICENSE shipped, the Usage Policy linked with its under-18 note, "Not an official Meta product", and that Meta didn't make, review or endorse the adapter); Provenance (Muse Muse, the job, its public page, the dataset repo, `muse_muse_run.json`).
- The template, the base model and its revision, and the trainer's settings are read from `GLIMMER_PY` itself (`glimmerTemplate`), so the card can't drift from what the recipe does; a source that no longer has one of them fails the publishing. The revision is `adapter_config.json`'s when it has one, else the recipe's. The system message is the one the run trained and answered under: with the short student prompt, the run's `student_system` metric, else what glimmer.py's `student_system` gives (ported as `studentSystem`, and checked against the Python in the tests); with the full one, the dataset's own system message (that metric then only describes it). A job from before the param, with no student prompt in its params or its metrics (run 1), counts as full, since glimmer.py always trained that way then.
- The dataset card is the dataset's, shared by every job trained on it, and `hubFinishStep` writes it only once the publishing job's model repo is committed and verified: `pretty_name`, `license: apache-2.0`, `task_categories: [text-generation]`, `size_categories`, machine-generated annotations and language, `source_datasets: [original]`, tags, and a `default` config over `data/train.jsonl` and `data/eval.jsonl`. Then "Why this exists" as the latest public model published from it tells it (with a line naming that model when there are several), the task, the files and their counts, the fields, how it was made, the split (the held-out count, near-duplicates at 70% of shared words kept out of train), the cost, Models trained on it (that model first, then every other published public one, newest first, `publishedHubModels` in the store, each with its run's public page), the license with the note that the dataset's writer (its `writer_model`, Muse Spark 1.3 when it has none) wrote all of it through Meta's Model API, and its provenance. A job whose publishing fails never changes it.
- `muse_muse_run.json`: the job (its settings and only the public metrics, `PUBLIC_METRICS`: never a cache path, a Blob URL or anything about the instance), the base model and revision, the system message, the dataset with its writer (`dataset.writer`), the judge (`eval.judge`), the eval summary with every item and its verdict, and who wrote the story (`story.by` and, for a model's story, `story.model`). Every model a card or the record names comes from the records, Muse Spark 1.3 when one has none (see Which model did the work): the lead ("learned one task from ..."), What it does ("the way ... answered those prompts"), the result sentence, the Results section's judge and whose reference it scored against ("its own reference answer" only when the judge wrote the dataset too), Limits, License and the dataset card.

The story (`hubStoryStep`): Muse Wonder (`STORY_MODEL`) through the platform's Meta client, effort low, saved with `storyModel`, from `storyRequest`'s facts: the dataset's title, task and writer (from its record), what Muse Muse is (it turns an example or some inspo into a working product on Meta's models, and the brief writer is its first step), that the adapter comes from Muse Muse's fine-tuning lab, and why teach an open 30B model you can run yourself what the dataset's writer does, and the admin's why when there is one. No count and no result are among the facts, and the instructions (`STORY_INSTRUCTIONS`) ask for none: right after the story the card gives the dataset's counts and the eval's result itself (`resultText`, with the writer and the judge from the records: "Muse Spark 1.3 wrote the dataset's 24 examples: 16 to train on and 8 held out. On 8 held-out prompts, judged blind by Muse Spark 1.3, the tuned model was better on 8 of 8, with an average score of 8.63 out of 10 against 1.88 for the base model."), so the story's result is in it and no number in it comes from a model. The instructions also ask for at most 100 words (about 80 is the aim), plain words, no em dashes, only the facts given, the task in one short sentence (the card quotes all of it), the brief writer only when the task is writing those briefs (a story for another task once said the adapter was part of it), no claim that Meta made, backs or endorses it, and none that Muse Muse runs or uses the adapter. Its output budget is 6,000 tokens because the reasoning counts toward it (Muse Wonder bills its reasoning as output): at effort low Muse Spark 1.3 reasoned for about 1,500 tokens before writing about 200, so a budget of 1,500 came back "incomplete" with no text (a real call, Oct 28). It waits 120 s, with one SDK retry, since a Muse Wonder call takes 1.4 to 2 times as long. Its usage is recorded (`source "platform"`) before the story is saved; a saved story is kept, so a retry never pays twice. The card prints the admin's why just before the story, and Muse Spark 1.3 sometimes opened with it word for word anyway, so a copy of it is taken out first (`dropRepeatedWhy`). `storyProblem` then turns a story down when it is empty, longer than about 100 words (115 at most), has markup (a heading, a list, a link, a table, code, HTML, a "//" or "www." address), says Meta made, backs, sponsors, approves or helped with the adapter or calls anything official, or states a number, a count word, a result or a comparison with the base model (`CLAIM_WORDS`: "eight", "twice", "won", "scored", "base", ...) that the task, the title or the why doesn't use itself; the names "Muse Glimmer 30B", "Muse Spark 1.3", "Muse Wonder 1.0" and "Apache 2.0" are fine. Then, and when `MODEL_API_KEY` isn't set, the spend cap is reached, the call fails or stops early, the template's story is used (`templateStory`: what Muse Muse is, the task's first sentence, and why). The job's log says which and why.

### Pages

- The admin job page of a glimmer-lora job has a Hugging Face card (`components/train/HubCard.tsx`): a status pill (`hubPill`), a sentence on where it stands (`hubStatusText`: off and why, waiting for the run or its judging, the files uploading as N of M, uploaded, publishing, published and public or private, failed and why), the model and dataset repos (links once published, `hubHref`: https only), who wrote the story, a link to an upload job in flight, the why the card prints in a textarea, and Publish, Retry or Publish again (`hubControl`), which confirm, then POST `.../publish` with the why. An "off" saved before publishing was turned on here shows as "Not published" with Publish; a "publishing" left by a run that stopped shows "Stopped" with Retry. ## Local files (glimmer-quantize)

Off unless `QUANT_ENABLED` is on ("1", "true", "yes" or "on"). A judged glimmer-lora adapter that is published on the Hub can have local files: GGUF builds in up to three sizes (Q3_K_M, Q4_K_M and Q6_K, `QUANT_LEVELS` in `lib/train/local-files.ts`) for LM Studio, llama.cpp and Ollama, each checked against the merged model before it goes to its own repo next to the adapter's. A glimmer-quantize job makes them on one GPU in the adapter's region and uploads them through the platform, as glimmer-lora uploads an adapter; its own trainJob publishes the repo with the GGUF card once it succeeds. The run-locally page, the device picker and drive orders read the result only through `localFilesFor`. The design: docs/VIBE_TUNING.md, Features 2 and 3.

```text
admin, on a judged and published glimmer-lora job's page: Make local files (POST /api/train/jobs/{id}/quantize)
  -> POST /api/train/jobs {recipe: "glimmer-quantize", params: {adapterJobId}}: the checks every GPU job gets, then the
     switch, the adapter (judged, the short student prompt, on its region's cache, published) and one local files job
     per adapter at a time; the platform writes levels, slug and trainChannel; the adapter's region
glimmer-quantize GPU (QUANT_PY in lib/train/recipes/quantize.ts):
  fail fast -> llama.cpp b11669 and Meta's files, each by sha256 -> the merge (Unsloth merged_16bit, on local disk)
  -> the merged folder's tensors and shards -> BF16 GGUF -> Q8_0 and each build -> the file checks
  -> ctx.hub_upload(out/): the builds that passed, system, params, tuned.jinja -> the metrics
its trainJob, after terminate: hubPlanStep (kind "gguf") -> hubGgufStep (the commit, read back)
  -> hubGgufFinishStep (the repo's visibility, the adapter's card, "published")
```

### Recipe, params and limits

- `glimmer-quantize`, "Make local files (GGUF)" (`lib/train/recipes/index.ts`): a 1x A100 SXM4 40 GB, then a 1x A100 40 GB, then a 1x A10 (`QUANT_GPUS`). The merge needs about 60 GB of RAM and the job asks for 180 GiB, so the A6000 and the RTX 6000 are left out. 110 minutes and $3.70 by default. It runs in its adapter's region with that cache mounted, as glimmer-serve does (`usesCache` and the adapter param); the cache is listed, never created.
- Params: `adapterJobId` (kind "adapter", required) and `publish` (1 by default; 0 checks the files and uploads nothing, so they are gone with the GPU). The platform writes `levels` (all three), `slug` (the adapter repo's, `ggufSlug`) and `trainChannel` (the adapter's, 0 when it has none) into the params itself (`quantParams`). A caller who sends one gets 400, and the Python checks them again (`read_quant_params`).
- `POST /api/train/jobs` refuses it with 503 `quant_off` while the switch is off; 400 `Adapter: <why>` for an adapter that isn't a glimmer-lora job's real adapter on its cache (`adapterProblem`), isn't judged, or trained under the full student prompt (`quantProblem`: the files and their card give every local app the one-line system message of the short one, and a job from before the param counts as full); 503 `hub_off`; 409 `adapter_not_published` with the reason; 400 when the adapter's dataset is gone; and 409 `quant_running` with the open job's `quantJobId` (one at a time per adapter; `earlierOpenQuantJob` backs out the later of two started at once).
- The estimate (`runEstimate`): 90 minutes, or 80 with the region's venvs on the cache (`QUANT_MINUTES`, `QUANT_CACHED_MINUTES`), until a real run measures it.
- A decision model's adapter is refused first, whatever else holds (`quantProblem`): its local files need a decision check (Q4_K_M's picks against the adapter's) that isn't built (see Decision models (decide mode)).

### The GPU side (lib/train/recipes/quantize.ts)

`QUANT_PY` is its head, `glimmerHelpers(GLIMMER_PY)` (glimmer-lora's venv, pinned uv and 4-bit model, the chat template's rendering, `student_system` and the event relay) and its own body, built as serve.ts and publish.ts are.

1. **Fail fast**, in seconds: no cache, no adapter at `<cache>/models/<id>/` or a dry run's stand-in, an adapter that targets a vision module, under 300 GB of local disk or 180 GiB of RAM, under 45 minutes left, or a dataset that holds out under 2 prompts or 6,000 characters. Each later stage needs its own time left to start: 40 minutes for the merge, 30 to convert, 25 to quantize, 18 for the checks and 8 for the upload.
2. **llama.cpp b11669** (v0.7.0, published 2026-10-15, after b10353, the first build that knows Muse Glimmer; commit `620d2225`). Each download is checked against its sha256 as uv is, and where each digest came from is in the comment above the pins: the release's `ubuntu-cuda-12.8-x64` build and its CUDA runtime (the digests GitHub's releases API gives), and the source archive (its sha256 as GitHub served it, the same on two downloads) for `convert_hf_to_gguf.py`, `conversion/` and `gguf-py/` only.
3. **The CUDA build.** Around b10353 the releases had no Linux CUDA build (VIBE_TUNING.md, fact 11), so the design weighed compiling one per region against an official CUDA container. b11669's release ships an Ubuntu CUDA 12.8 build with its CUDA runtime beside it, so every tool (`llama-quantize`, `llama-perplexity` and `llama-server`) runs from llama.cpp's own binaries, downloaded per job to local disk: nothing compiles on the GPU (no toolchain to pin, no build lock, no minutes lost the first time in a region), no container image to pull and pin, and none of the build on the cache, which bills per GB (only the converter's small venv is cached, step 5). `llama-server --list-devices` must list a CUDA device before anything runs on it.
4. **Meta's files**: `chat_template.jinja`, `tokenizer.json`, `tokenizer_config.json`, `processor_config.json` and `generation_config.json` of meta-models/Muse-Glimmer-30B at revision `cec94fcf` (`META_FILES`, each by sha256). `tuned.jinja` is Meta's template with two exact edits (the default reasoning strength low, and a generation prompt that opens `to=user`), and it must hash to `TUNED_TEMPLATE_SHA256`.
5. **The venvs**: glimmer's from the cache for the merge (`ensure_venv`), and the converter's own small one, `venvs/llamacpp-<hash>` on the cache under the same build lock (`CONVERT_INSTALL`: CPU torch 2.11.0, transformers 4.57.6 and the rest of the source's converter requirements, each pinned).
6. **The merge**, in a child on glimmer's venv under `ctx.run`'s stall watch: the 4-bit base and the adapter (`PeftModel.from_pretrained`, not trainable), then Unsloth's save-merged function bound to the PeftModel itself, with `save_method="merged_16bit"`, which downloads the 16-bit base, OfflineBase/Glimmer-30B-2026-Knowledge (`MERGE_BASE`), and merges tensor by tensor in fp32. `HF_HOME` is on local disk with the cache's 4-bit model linked in, so the 59.6 GB download never lands on the cache. Never `merged_4bit`, and never `merge_and_unload()` on the 4-bit model. The child also renders the expected prompt with training's own tokenizer and template, for the template check.
7. **The merged folder**: the base's 1,436 tensor names and shapes (`BASE_TENSORS_SHA256`, from Meta's safetensors headers, the same in r30b's), and the 16-bit shards' SHA-256 against r30b's 13 (`BASE_SHARDS`). Unsloth's merged_16bit finds the base from the model's `config._name_or_path` through its own name mapper, which knows only Unsloth's repos, so the merge child sets it to `MERGE_BASE` (OfflineBase/Glimmer-30B-2026-Knowledge) before saving: left as the nf4 build's name it would come back unchanged and be refused as a 4-bit base. Unsloth takes no revision for that download, so `MERGE_BASE_REVISION` only records which commit `BASE_SHARDS` were listed at. Unsloth downloads them with `snapshot_download(local_dir=merged/)`, so they land in the merged folder itself and are merged in place; the check reads the commit and etag (an LFS file's SHA-256) huggingface_hub records beside each one in `merged/.cache/huggingface/download/<shard>.metadata`, or, for shards Unsloth copied from an HF cache, that cache's blob names when they are the SHA-256 and the bytes' own hash otherwise. A shard that isn't one of r30b's 13 fails the job, and so does a merge that left no record of its shards in either place, since Unsloth asks for whatever OfflineBase/Glimmer-30B-2026-Knowledge's main is. `merge_base_revision` is recorded only once they matched, and the card names the base's shards only with it. Meta's files replace the ones Unsloth saved and a stray `chat_template.json` goes, so the GGUF embeds Meta's current template. The local `HF_HOME` is deleted.
8. **Convert and quantize**: `convert_hf_to_gguf.py --outtype bf16 --model-name muse-glimmer-30b-<slug>`, then `merged/` is deleted; `llama-quantize` from BF16 to Q8_0 (the closeness reference, never published) and to each level, then BF16 is deleted. Each file must be a GGUF of the architecture `muse-glimmer` with 731 tensors and Meta's template in it (read with gguf-py's `GGUFReader`).
9. **The file checks** (below). The builds that failed are deleted, and `system`, `params` and, for an adapter trained before `trainChannel`, `tuned.jinja` are written next to the ones that passed.
10. **The upload**: `ctx.hub_upload(out/)` (see Three repos per run). A skip or a file that didn't arrive fails the job: its files exist only on this GPU.
11. **The metrics**: per level `<level>_bytes`, `_sha256`, `_kl_mean`, `_kl_p99`, `_top_token_pct` and `_passed`; `channel_final`, `channel_total`, `channel_passed`, `agreement`, `agreement_total`, `template_check`, `checks_passed`, `published_levels`, `system`, `train_channel`, `tuned_template`, `hub_uploaded`, `hub_repo`, `hub_files`, each stage's seconds, `gpu`, `llamacpp`, `llamacpp_commit`, `merge_base`, `merge_base_revision`, `tensors`, `cached_venv`, `cached_weights`, `levels` and `adapter_job_id`, and a summary.

### The file checks

None of them calls Meta. They are the gates docs/VIBE_TUNING.md "The file checks" sets:

- **Template.** `llama-server --jinja` on Q4_K_M (local only, 4 slots, an 8K context in all, `--no-mmproj --no-webui`; for an adapter trained before `trainChannel`, `--chat-template-file tuned.jinja --skip-chat-parsing --reasoning off`). `/apply-template` with the system line and held-out prompt 0 must render the merge child's expected prompt character for character, with the opened final channel for tuned.jinja. Otherwise the job fails.
- **Closeness.** `llama-perplexity --kl-divergence-base` from Q8_0 over the held-out prompts and references as plain text (it reads no chat-template token in its text), in 512-token chunks, then `--kl-divergence` for each build. A build passes at a mean KL divergence of at most 0.08 (Q3_K_M), 0.03 (Q4_K_M) or 0.005 (Q6_K) (`QUANT_KL_MAX`). One over its limit is left out and the others are still published; none passing fails the job.
- **Channel.** Every held-out prompt on Q4_K_M under a stock app's prompt (tuned.jinja for an old adapter), greedy, 1,024 new tokens. At least 90% (`QUANT_CHANNEL_MIN`) must end with a non-empty final answer with no format leaked, or nothing is published: "The local files keep thinking instead of answering".
- **Agreement**, shown and never a gate: how many Q4_K_M answers start with the same 200 characters as the adapter's own eval answers. The dataset route pages a glimmer-quantize job its adapter's dataset, each held-out item with the adapter's `tuned` answer.

### The GGUF repo and its card (lib/train/hub-cards.ts)

- **Files**: the builds that passed (LFS); `system`, `params` and `tuned.jinja` when it applies; `README.md` (the card); `LICENSE` (the base model's, which must still be the Apache License); and `muse_muse_quant.json` (the job, the adapter and its commit, the merge, the template's revision and sha256, llama.cpp's build, the system line, each build with its numbers and limit, the builds left out, the checks and the small files' digests).
- **The card** (`ggufCard`): front matter the Hub's validator takes (`base_model: meta-models/Muse-Glimmer-30B`, or OfflineBase/Glimmer-30B-2026-Knowledge for files merged into r30b, with the Derivative's license front matter and block as on the model card, `base_model_relation: finetune`, `pipeline_tag: text-generation`, `license: apache-2.0` (a Derivative's: `license: other` with `license_name: apache-2.0-and-muse-model-license`), `language: [en]` for a task in plain ASCII, the tags `gguf`, `llama.cpp`, `muse-muse` and `lora-merged`, and the dataset repo), a lead that names the adapter's repo and the model that taught it (its dataset's `writer_model`, Muse Spark 1.3 when it has none), then the design's sections in its order: Which file for my computer, Run it (LM Studio, the Llama app, llama.cpp and Ollama, in versions that know Muse Glimmer: llama.cpp b10353 or later, Ollama 0.32.8 or later), Prompt it the way it was trained, How close the files are, How it was made, Files and checksums, Limits, License and Provenance. Every number comes from the records: the job's done metrics and row, its adapter's hub state and metrics, and the dataset. The files' system line must be the one the adapter trained under, or publishing fails.
- **Visibility**: made private first, and public only when `HF_PUBLIC` asks for public repos and the adapter is public on the Hub (`ggufOpen`), as read back from the Hub. A repo another local files job of the adapter already published keeps its visibility when the files are made again, so a second job (whose publishing may still fail) never takes them off the public pages; an adapter made private takes it private either way (see Three repos per run).
- **Ollama**: the card's Modelfile is `ggufModelfile(file, system, trainChannel)`, the same the run-locally page gives for the build it set up (the TEMPLATE and its four stops for an adapter trained before `trainChannel`), and the model is named by its slug (`ggufOllamaName`) on both. The llama.cpp command has `-c 8192 -np 1`, as the memory table counts.
- `hubGgufStep` asks the LFS batch about every build again (one the Hub doesn't store fails publishing for good: "Make local files again."), checks the small files again, and makes one commit where anything differs. `hubGgufFinishStep` sets the visibility, points the adapter's card to the repo (left to the adapter's own run while it is being published; a failure is logged and never fails these files) and saves "published" with `public` as the Hub reports it.

### Emulator runs (SIM_TUNE)

Off unless `SIM_TUNE` is on, and it also needs `NATIVE_LAB`. Written and tested against fakes; nothing has run on the real lab. On an admin's page of a tuned model, `SimTuneCard` (`components/train/SimTune.tsx`) queues a `gguf_emu` job on the lab's queue (`POST /api/train/jobs/{id}/sim-tune`): the smallest of `localFilesFor`'s files goes on the Android emulator, llama-server loads it, it gets the fixed `SIM_TUNE_PROMPTS` under the model's system line, and the card shows tokens per second, load time, peak memory and the answers, always beside a label saying it is an emulator and not a phone.

- **Too big today.** `pickSimTuneFile` refuses a file over `SIM_TUNE_MAX_GGUF_MB` (3072 by default, to fit the emulator's 4 GB). Local files are only made for 30B Glimmer, whose smallest build is 13.68 GB, so every current model gets that refusal, in those words. A model with a smaller local file passes. Raising the cap alone won't help a 13.68 GB file: the emulator would need over 16 GB of RAM and a bigger disk, on a box that also has to fit the job's 900 s limit.
- **Public only.** The lab box holds no Hub token.
- **No migration.** `native_jobs` needs a run, build and product, so these jobs hang off one hidden disabled product, `sim-tune-emulator-runs`, with one build marked failed. It appears once in its first admin's own lists. Its runs have the origin `agent`, which the product views skip, and stay `running` since nothing reads them.

### localFilesFor (lib/train/local-files-server.ts)

The contract the pages read. `localFilesFor(adapterJobId)` takes the newest glimmer-quantize job of the adapter that succeeded, had its GPU shut down, and whose metrics say its checks passed and its files reached the Hub (`latestQuantSource` in the store); one whose repo is published comes before newer ones that aren't, so a new run never hides files already out. Its `files` are the builds the metrics say passed, smallest first, with their bytes and sha256, and once published only those the repo holds as those bytes. `repo`, `commit` and `public` come from its hub state (null, null and false until published), with `systemLine`, `needsTunedTemplate`, the dataset's `title` and the `slug`; `public` holds only while the adapter itself is published and public too, so an adapter made private takes its files' pages and drive orders with it at once. Null when there is none. The types and `QUANT_LEVELS` are in `lib/train/local-files.ts`, which client components import; `localFilesFor` reads the database, so it is in `lib/train/local-files-server.ts`, which only server code (pages, routes and scripts) imports: a client component that reached the store would pull its database driver into the browser bundle, which `next dev` refuses.

### Pages

- **Make local files** (`MakeLocalFiles` in `components/train/LocalFiles.tsx`), on an admin's page of a glimmer-lora job that succeeded, under its Hugging Face card: where the adapter's files stand (not made, making, published, private, failed or off), why they can't be made now, a link to the newest local files job, a link to the run-locally page once there are files (admins see its guide while the repo is private, the way to test it), and the button, which confirms first and says the files go public on Hugging Face when the adapter is. Files that passed and are publishing show "Publishing" and no button; once there are files, "Make local files again" is the quiet outline button, since it pays for another run. A failed local files job's card links back to the adapter's. It reads `GET /api/train/jobs/{id}/quantize` (`{quantOff, hubOff, problem, latest, files}`) when it opens and every 10 s while a job makes them; `POST` there starts the job through `POST /api/train/jobs`, with its checks and its replies.
- **A local files job's own card** (`QuantFilesCard`): each build with its size, its mean KL divergence against its limit, how often its top token is the same, and its result; the channel check and the agreement; where the repo stands, with its link once published; and Publish, Retry or Publish again (`ggufControl`), which confirm first. Nothing to press while publishing is off, while the job runs, after it failed, or when its files didn't all reach the Hub.
- The sentences are in `components/train/format.ts` (`quantRows`, `ggufStatusText`, `ggufControl`, `makeFilesText` and the rest).

## Fine-tune like a build (TUNE_COMPOSER)

Owner, Oct 31: "A new fine tuning job should be almost as simple looking and just about as simple as a regular muse muse build." With `TUNE_COMPOSER` on, admins get `/fine-tuning/new`: one box, "What should your model do?", with a CSV or JSONL of the person's own examples (or a few `Q:` and `A:` lines pasted under the note), the Make page's look and a folded Training setup. Send turns the page into the room at once: the person's words as a bubble, "Muse Wonder is drafting the plan", then the plan card with the mascot presenting and Start, Change it and Advanced. Start begins the run and the page becomes its room at `/fine-tuning/runs/{id}`. With the flag off both pages and the three routes below answer 404, and nothing else changes: `components/train/__tests__/tune-flag-off.test.tsx` checks that the build composer, the build setup, the build room and `/fine-tuning` render byte for byte as they did before (SHA-256 of each render, taken from the code before the shared edits).

Built so far from the design (section A of "Fine-tune like a build", Oct 31): the composer, the plan, the run room, the verdict and Where it runs (stage 1), then `launchJob`, the `tuneRun` workflow that launches the GPU on its own, `runs/{id}/start` and Advanced's training steps (U3), with their tests. Not yet: the chat route on the demo GPU, the build room's own-model row, and a stop route.

**The run is its dataset.** No migration: a run is a `training_datasets` row, its room is keyed by the dataset's id, and its training job is the newest `glimmer-lora` job whose `params.datasetId` names it (`latestTuneJob` in `lib/train/tune/run-store.ts`). A dry run never counts, and nor does a job that failed before any GPU launched (no instance id, no launch time: two starts raced, its workflow couldn't start, or the sweep failed it while queued), so the run has no job and Start training launches again; a job that launched and then failed is still the run's job. Stages (`tuneStage` in `lib/train/tune/view.ts`): writing, checking (at least 16 to train on and 8 to score with), waiting, training, scoring, ready, failed, stopped. The mascot presents while planned, failed or stopped, builds while anything runs or waits, and stands as the pair once scored (`TUNE_ART` in `components/train/room/steps.ts`, which also maps the run onto the chat kit's `StepItem` rows).

**Starting training** (U3). Start on the plan card starts the run: `startTuneRun` saves the dataset, starts `makeDataset`, keeps the run's training steps and starts the `tuneRun` workflow (`lib/train/tune/run.ts`, steps in `run-steps.ts`). It looks at the dataset every 30 s until it is ready; checks the examples (`checkExamples` in `run-launch.ts`: a chat dataset, at least 16 to train on and 8 to score with, still 16 once conversations over 2,048 tokens are left out, and nothing the content seam finds); then launches through `launchJob` with the run's settings: `glimmer-lora`, its dataset, steps, LoRA rank, learning rate, the short student prompt and publish 0, on the A100 SXM4 first, up to 90 minutes and `TRAIN_JOB_MAX_USD` (`launchForRun`). While no GPU is free (`no_capacity`), the platform's GPUs are in use (`too_many_active`), the day's cap (`daily_cap`), the sweep (`sweep_not_running`), Lambda not answering or Meta's spend cap (`paused`: scoring needs it) say no, it tries again every 5 minutes for up to 2 hours. Any other refusal ends it. It never launches for a run that was stopped, and once the job exists it ends: the job is a `trainJob` workflow of its own. The launch holds the run's one claim (a 5-minute window and the next) and looks for the run's job first, so the workflow and Start training never both start one.

No migration: what a run keeps besides its dataset is in `rate_limits` (`lib/train/tune/run-store.ts`): its heartbeat `tune-run:<id>:<state>` (one row a try, the waiting reason as the state, dropped by the hourly cleanup), why it ended without a job `tune-run-end:<id>:<code>`, a stop `tune-run-stopped:<id>` and its steps `tune-settings:<id>:steps` (both under a window that never starts, as the native downloads count is), and the claim `tune-launch:<id>`. The room reads them (`runMarks` and `tuneStage`): a fresh "checking" heartbeat is the checking stage; a fresh waiting one is the waiting stage with the reason as the working step and in the steps panel, titled by what it waits for ("Waiting for a GPU", or for the daily budget, the spend cap, the GPU check or Lambda); a failed check fails the run with why; and with no fresh heartbeat and no job, the run waits on a person ("not_started"), saying why the last try ended when one did. A heartbeat counts as fresh for 11 minutes, two tries and a minute.

In the room the waiting spot is **Start training** (`StartTraining` in `TrainRoom.tsx`, POST `runs/{id}/start`), or Try now while the workflow is still trying, with a small "Use the full form" link for admins to `/fine-tuning?dataset=<id>#new-job`. Since every launch passes publish 0, nothing is published until someone presses Publish on the job. Once a job trains on the dataset, the room follows it: training, scoring, then the verdict, the eval results, the job's live demo (Try it live while one is open, else Start a live demo, read by `app/fine-tuning/runs/live.ts` the way the job page reads it), for admins the Hugging Face card and Local files, and Where it runs. The GPU's log, its limits and Stop stay on the job's page, which the room links.

**Defaults** (`lib/train/tune/cost.ts`): `TUNE_DEFAULT_EXAMPLES` examples (200), `glimmer-lora`, 120 steps, LoRA rank 16, learning rate 2e-4, the short student prompt, publish off, the A100 SXM4 first, up to 90 minutes and `TRAIN_JOB_MAX_USD`. The plan's name becomes the dataset's title, written as a role ("You are " + name). Advanced changes the number of examples, from 40 (`TUNE_MIN_EXAMPLES`: a run needs 16 to train on and 8 to score with, and a dataset often comes back a little short, so the datasets route's own 20 would fail after the writing was paid for) to the caller's most (`tuneExamplesMax` in `caller.ts`, 1000 today; open-train returns its visitor cap there, since the plan's token signs the task but not the size), and the training steps, from 10 (the recipe's least) to as many as fit in the run's time limit on the A100 with the model cached (`maxStepsFor` in `lib/train/tune/settings.ts`: 350 at 90 minutes); the card prices and times them as they change. The GPU and the limits stay on the full form.

**Cost, honestly.** The plan card prices a run as: examples $3.08 to $6.76 for 200 (an estimate at Muse Wonder's prices, `datasetCostRange`; what Muse Wonder costs per example hasn't been measured), the GPU up to its hard limit, and scoring about $0.18 to $0.56 (an estimate), and the card says which parts are estimates. Drafting a plan is one Muse Wonder call, about $0.01 to $0.03 (an estimate). The server makes every setting but the number of examples, and every cost, again on Start.

IQ1_S then gets its own template and answer check on 30 held-out prompts, with 90% needing a final answer. Any problem leaves out that build alone. `LOW_BIT_KL_MAX` is null in both `lib/train/logic.ts` and `QUANT_PY`: the only IQ1_S KL measured (1.183) came from an adapter on an older base, and Q3_K_M's limit says nothing about a file this small. - **It stays out of `LocalFiles.files`.** The one-bit file is `LocalFiles.lowBit`, so the run-locally guide and drive orders never offer it.
- **Memory.** Where it runs replaces "Not on a Jetson Orin Nano" with the measured 6.53 GB file, 7.3 GB to run and 2.4 tokens a second on an x86 stand-in, and the board's 8 GB shared with the OS, labeled not run on a real board (`docs/JETSON_TODO.md`). ## Tuning loop (TUNE_LOOP)

Off by default. On a run that trained and was judged, an admin sets a target score, a spend cap, rounds (1 to 5) and new examples a round (`app/api/train/loops`, `lib/train/tune/loop*.ts`, `/fine-tuning/loops/{id}`). No migration: the record is in `rate_limits` and a round's datasets have fixed ids (`lib/train/tune/loop-store.ts`).

A round: `loopNextStep` decides from the last verdict and, to go, starts `makeDataset` on a writer dataset whose task adds the weak prompts. `loopMergeStep` makes the round's dataset: the last round's training rows and the new ones, with the source's title, task and kept-aside prompts unchanged, since the title is the training line and eval indexes must mean the same prompt every round. Then the usual examples check, and `launchForRun` with the source job's settings (`newVersionPlan`), publish 0 and a new adapter from the base.

- **The score.** Kept-aside prompts split in pairs (`isSealed`): the writer sees weak prompts from the working half only, and any new row near any kept-aside prompt is dropped. The target counts only on the sealed half, which also has to pass the verdict's chat rule (`chatPasses`). A run needs 16 kept-aside prompts, so 8 are sealed.
- **The cap.** Covers the loop's own rounds, not the run it started from. Each round's job gets a hard dollar limit of what the cap leaves after writing and the judging estimate (`roundBudget`). The writer is checked every 30 s and stopped when it eats into that. Judging is an estimate, so it could carry a loop slightly past the cap.
- **Steps.** A round's steps grow with its rows, so it gets the same passes over its data as the source (`roundSteps`), within the job's time.
- **Stop.** `stopLoop` marks every round's run stopped ahead of time, fails a writer in progress, stops a job and ends the loop at once.

Nothing here has run for real. A first real run must check: `start(makeDataset)` from inside a step, the workflow's discovery of `tuneLoop` and its polling over hours, that a job's eval indexes are positions in the dataset's eval list, `EVALS_MAX` when a source holds over 60 kept-aside prompts, the score moving by more than the judge's noise between rounds, Meta's cost per example against the estimate, and how the extra datasets and each round's public result read on the Lab pages.

## Data research (TUNE_RESEARCH)

Owner, Nov 1: a deep research for data that would help a fine-tune. Off by default, admins only (`requireAdminOrAutomation`, `pageViewer`): with `TUNE_RESEARCH` off the routes and pages answer 404, the New dataset card is unchanged and no dataset reads notes. Code in `lib/train/research/`, migration `0029_tune_research` (additive: a `training_research` table and `training_datasets.grounding`). None of this has run against Meta or a real source yet: only the rules' tests have run.

**Starting.** The New dataset card's Find data first takes the task, shows the estimate and the cap, and posts to `POST /api/train/research {task}`. Five runs an hour per admin (`tune-research:<id>`).

**The run.** `researchData` is a durable workflow on Muse Wonder (`TEST_MODEL` where that is on, never production): up to 4 narrow sub-questions; one `responses.create` for each, with Meta's `web_search` as the only tool, at most 4 built-in calls and 3,000 output tokens, `include: ["web_search_call.results"]`; then a report written with no tools. A retried step finds its saved finding and doesn't pay again.

**Spend.** Every call goes through `recordUsage` (source "platform") and onto the run's cost, searches at $2.50 per 1,000 queries. Each step checks `spendPaused` (`DAILY_SPEND_CAP_USD`). A search starts only if its worst case and the report's still fit `TUNE_RESEARCH_MAX_USD` ($2 by default), otherwise the report is written from what was found and says so. The estimate and worst cases in `estimate.ts` are at Muse Wonder's prices and aren't measured: a call's output and search count are capped, its input isn't, so the cap holds to that estimate.

**Nothing uncited.** A report names each source by its number in the list of links the searches returned (`searchCitations`: `web_search_call.results` and `url_citation` annotations, public http(s) only), so the model can't write an address. A number outside the list is dropped and counted in the report's note. License, size and the rest are a model reading web text, and the page says so.

**Picks.** Write a dataset (`POST .../{id}/dataset {picks, count}`) starts `makeDataset` on the original task with the picks' notes in `grounding`, up to 4,000 characters and scanned for PII. The writer reads them as background (told they are reference, not instructions); they are never in a training example's system message or the card's task.

**Import** (`POST .../{id}/import {sourceId, licenseConfirmed}`, 10 an hour). Decided from the stored source: personal data "no" only; a restrictive license never; a Hugging Face dataset's page or an https `.csv` or `.jsonl` file only. `licenseClass` is an exact list, so CC BY-NC, share-alike and "MIT-like" aren't open. For a Hub dataset the Hub's own license field must be open and it must be public and not gated; rows come from the datasets server. For a plain file the admin confirms they read the license, since nothing but the model says what it is. Limits are the decision upload's 4 MB and 3,000 rows read, at most 1,000 kept, at least 40; rows at a parser's length cut are dropped, near-identical prompts merged. Any `piiFindings` hit refuses the whole source. `safeGet` is https only, checks every hop for public addresses and again in the socket's own DNS lookup, follows 3 redirects at most, stops at the byte cap and sends no credentials.

An imported dataset is ready at once with writer_model `public` and a note naming its source and license. Its rows aren't shown on the public Lab page, it never auto uploads, and its dataset repo stays private (`keepDatasetPrivate`). Nothing here starts a job: training still takes New job or Start.

## Flash drive orders (docs/VIBE_TUNING.md, Feature 6)

A model with public local files (`localFilesFor`) can be ordered on a USB stick. The site takes no payment: a request saves the model, the build and a US shipping address, the owner emails an invoice from their own tool and moves the order along at `/fine-tuning/orders`, and `scripts/drive-bench.ts` flashes and checks the stick on the owner's Mac. Off unless `DRIVE_ENABLED` is on. Code: `lib/drive/` (rules in `logic.ts`, the table in `store.ts`, the image in `image.ts`, the bench in `bench.ts`), table `drive_orders` (migration `drizzle/0007_drive_orders.sql`), pages `/orders/new?model=<job>`, `/orders/{id}` and `/fine-tuning/orders`, the offer on a model's public page (`components/drive/DriveOffer.tsx`), and the drive's own files in `drive/`. The request page shows the device picker and its verdict above the form (`LocalGuide` with `guide={false}`: no download, disk box or app guide), so nobody orders a drive their computer can't run, and each single size says which computers it is for.

- **Statuses** (`lib/drive/logic.ts`, every move checked against who may make it): requested, invoiced and paid (the admin), flashing and checked (the bench; a FAIL puts the order back to paid), shipped and delivered (the admin), cancelled (the buyer until flashing, an admin until shipped).
- **The request** (`POST /api/drive/requests`): not cross-site, past a bot check that passes everything until the shared one exists (`lib/drive/bot.ts`), with the 18+ box, the terms version (`DRIVE_TERMS_VERSION`, the text in `lib/drive/terms.ts`) and a US address; 3 a day per client by the HMAC of its IP or of a random browser cookie (`DRIVE_CLIENT_REQUESTS`) and 20 for everyone (`DRIVE_DAILY_REQUESTS`), counted in the same transaction as the insert. The answer is the order link, shown once; the browser also keeps its secret in an HttpOnly cookie. Only `hashToken` of the secret is stored. `DRIVE_NOTIFY_URL` gets one line without the buyer's details, and can't mention anyone: Slack's copy is escaped and Discord's sets `allowed_mentions` to none, since a vibe run's title comes from what someone typed.
- **Privacy**: the buyer's name, email and address (with the tracking number, the invoice's reference and amount, and the notes) are cleared 60 days after delivery or cancellation, and the quota keys after 30 days (`purgeDriveOrders`, run after each request and before the admin queue reads). An order still marked shipped counts as delivered 14 days after it shipped (`DELIVERED_BY_DAYS`), so a parcel nobody marked Delivered loses its buyer's details 74 days after shipping.
- **Where to write** (`DRIVE_CONTACT_EMAIL`, optional): shown on the request form, the order page and the page for an order the browser can't open, written onto the drive (Start Here, the README and `support/model.tsv`, which the launchers and Verify read, with the model's page for Try it live), and given to "Stuck?" on the run-locally page. Without it the pages say to reply to the invoice's email. A cancel after payment says the payment is refunded, and the admin queue flags "Refund owed".
- **The bench** (`GET /api/drive/bench/next`, `POST .../{id}/flashing`, `POST .../{id}/flashed`) takes the bench token, whose hash is `DRIVE_BENCH_TOKEN_HASH`, or an admin. The hash is the token's plain SHA-256 (`lib/drive/token.ts`: the token is 32 random bytes), so `scripts/drive-bench.ts token` makes a pair with no platform secret and the bench Mac's `.env.local` holds nothing of production's. It sees no buyer details. The script sends the token only to an https origin (plain http only on localhost), and gives up on a call after 60 s. It offers only removable USB disks of 30 to 35 or 60 to 70 GB, each listed with its volumes and how much they hold; it erases one only after its disk id is typed, and one that isn't blank (a volume over 100 MB, or one it can't read) only after its volume's name is typed too. The order is claimed before the last look at the disk, and `erase` reads the disk once more right before `diskutil eraseDisk`, refusing unless it is the same disk (`sameDisk`: id, name, size, bus, `DeviceTreePath` and media UUID, and its volumes' names), so a disk that took the stick's id while the claim was in flight is never erased; a stop then leaves the order claimed, and the next run starts with it. It writes the image, the model files, `PROVENANCE.json` and `SHA256SUMS`, strips extended attributes, ejects, and after a replug reads every file back. Every disk command goes through `DiskOps`.
- **The image** (`lib/drive/image.ts`, `scripts/drive-image.ts`): llama.cpp b11669 (v0.7.0) for macOS arm64, Windows Vulkan and Windows CPU, each archive checked against the sha256 the GitHub release API lists, with only the server and the libraries it loads kept (exFAT has no symlinks, so the macOS libraries are copies); Meta's LICENSE and Usage Policy verbatim at a pinned commit; the GGUF repo's card and, for an old adapter, `tuned.jinja` at the files' commit; `CHANGES.md`; and `support/builds.tsv`, the device picker's own verdict (`lib/vibe/device.ts` `pickBuild`) for every Mac and PC size, which both launchers read. The launchers never download anything: they pick the build, offer to copy it (checking its sha256), and start `llama-server` on 127.0.0.1 with `--offline` and the system message preset through `--ui-config-file`.
- **Tests**: `lib/drive/__tests__/` (logic, the store on PGlite with the shipped-order purge, the routes on PGlite with the bench token's SHA-256 and a webhook that mentions nobody, the image with the Mac launcher run against shims, the bench with a folder as the stick: a disk swapped in while the claim was in flight, volumes that need their name typed, https only and a hung platform) and `components/drive/__tests__/pages.test.tsx`.
- **Not proven yet**: a real stick (its sustained write, the bench's diskutil steps, exFAT and the `.command` on a clean Mac, the Windows scripts on a real PC with and without Smart App Control), the macOS libraries copied out of their symlinks running, the web UI picking up `systemMessage` from `--ui-config-file`, a real `localFilesFor` answer, and the bot check.

## Run it on a hosted GPU (HOST_TUNED, off by default)

A tuned model that passed gets a Run it section on `/models/{id}`: one click deploys it on Fireworks, Modal, Baseten or Lambda, on the platform's accounts and at the platform's cost. People bring no key or account. Code is in `lib/train/host`. **No route here has run against a real provider or GPU.**

| Provider | How it deploys | Serves | Billing used for limits |
|---|---|---|---|
| Fireworks | REST: uploads the adapter from Hugging Face, then a scale-to-zero deployment | Plain Glimmer adapters with trainChannel 1, or Llama 3.2 3B adapters, with a list of target modules, rank 4 to 64. Refuses r30b (no r30b base) and trainChannel 0 (no way to open the final channel), so no adapter trained so far qualifies. Neither base is on its documented addon list, which says others need an enterprise account. | $8/h clock, estimate |
| Modal | Generated vLLM 0.32 app, `modal deploy` (CLI pinned at 1.6.3) in a Vercel Sandbox | Anything on the Hub with a pinned base | $4.85/h Glimmer, $1/h small, estimates |
| Baseten | Truss (pinned at 0.18.37) in a Vercel Sandbox, Management API for status and delete | Anything on the Hub with a pinned base | $6.50/h Glimmer, $0.85/h small, estimates |
| Lambda | The lab's `glimmer-serve` job, reused | What `adapterProblem` allows: r30b adapters on the lab cache | The job's real cost; reserves its $5 limit |

A plain Glimmer adapter shows Modal and Baseten as unavailable, because its job records no pinned full-weights commit. On Modal and Baseten, a trainChannel 0 adapter (every one so far) runs under `TUNED_TEMPLATE`, which opens the final channel as it was judged, with the lab's extra stops; a trainChannel 1 adapter runs with `--reasoning-parser muse_glimmer`. A provider with an unset key shows as unavailable, naming the env var.

**Limits, in code, with env overrides:** `HOST_TUNED_DAILY_USD` ($25 across providers), `HOST_TUNED_MAX_LIVE` (2, held by a unique index on slots), one per model (a unique index), `HOST_TUNED_IDLE_MINUTES` (15), `HOST_TUNED_MAX_MINUTES` (240), admins only until `HOST_TUNED_OPEN`, then only on a model the person trained, and never anyone without a session of their own (the shared guest, or OPEN_ACCESS=admin's stand-in admin, so a paid test needs a real admin sign-in). Before starting, an endpoint's minutes are cut to what the money left can cover, and that cost is reserved as a `hosted` usage row, so it also counts against `DAILY_SPEND_CAP_USD`. A long-running endpoint therefore holds much of the day's budget until it stops, when it settles at the clock's cost.

**Stopping:** `/api/cron/host-sweep` runs every 5 minutes, also with the flag off. It stops anything past a limit. If the budget or rows can't be read, it leans to stopping, including everything a provider lists under the `mm-host-` prefix. Resources are named before any provider call, so a crash can still be stopped. A stop that fails stays `stopping`: no traffic, money held, retried. A stop that arrives while a deploy may still be running (no ref, under 6 minutes old) only refuses traffic and holds the money, and the deploy stops the resource when it returns; a row with no ref past 6 minutes is a dead deploy, and the sweep stops it by name. On Lambda a stop with no ref only touches a job with this feature's title started since the endpoint's row, so it can't stop a demo window's job. Modal isn't listed in the sweep, since that would need a sandbox each time. It relies on its name, and on scaling to zero once it gets no traffic. So real idle stops can be up to 5 minutes past the limit, and Lambda's run at most 45 minutes (30 serving plus 15 boot).

**Calling it:** `POST /api/gateway/hosted/v1/chat/completions`, whole replies only, with the owner token shown once at deploy (`mmh_...`, hash stored) or a live product token whose product owns the model, with `model` set to the tuned job's id. Each answer is a `hosted` usage row with its tokens at $0: the money is on the endpoint. Addresses, refs and hashes never reach a browser (`lib/train/host/view.ts`). Modal's vLLM key is derived per endpoint and never stored. `HOST_HF_TOKEN` if set, else the platform's HF token, reads private repos, and reaches providers only as a Modal secret or a Baseten secret on the platform's own accounts. Set a read-only `HOST_HF_TOKEN` before the first deploy.

**Unproven, needs the first paid test:** every provider call shape (from docs, with faked responses in tests); the Modal and Truss commands, whose flags and messages were read from each CLI's source but never run, and Modal's address parsing; `TUNED_TEMPLATE`, the stops and the reasoning parser on a real adapter under vLLM 0.32 with Glimmer LoRA, which nothing here has served; the sandbox's firewall letting the CLIs through; Truss's `/app/data` path; cold starts; prices beyond list; Fireworks accepting any uploaded addon on these bases. Fireworks' terms 3.3(v) (uploaded input has no machine-generated content) is an open legal question for models made with generated data. Baseten's terms 4.3(b) matter if this is ever charged for.

## Try a tuned model (TRY_TUNED, off by default, also needs HOST_TUNED)

A public chat on `/models/{id}`, for a model with a public page that passed judging. Code: `lib/train/host/try.ts`, `app/api/models/[id]/try`, `components/models/TryTuned.tsx`. The tuned model and the model it started from answer on the same GPU, one after the other. **No part of this has run against a real provider or GPU.** A paid test needs a real admin sign-in and provider keys held only in Vercel, so it is blocked here.

**A visitor can wake a sleeping model, inside these limits.** This is the one exception to "never anyone without a session" above. It is this build's reading of the owner's brief and still needs confirming: `TRY_TUNED_WAKES_PER_DAY=0` leaves answers on a model that's already awake and no guest wakes. A plain Glimmer adapter can't be woken this way at all, since only Lambda serves it.

| Limit | Default | Held by |
|---|---|---|
| Wakes per visitor (network address) per UTC day | 1 | counter |
| Wakes per model per UTC day | 2 | counter |
| Wakes per UTC day, every model | `TRY_TUNED_WAKES_PER_DAY`, 4 | atomic counter |
| Dollars wakes may promise per UTC day | `TRY_TUNED_DAILY_USD`, $10, held to `HOST_TUNED_DAILY_USD` | atomic counter, taken before any provider call |
| Longest a wake may bill | `TRY_TUNED_MINUTES`, 60, held to `HOST_TUNED_MAX_MINUTES`. Under 35, no wake can start | the endpoint's stop time, 5 minutes sooner because the sweep runs every 5 minutes |
| Answers per visitor | 10 in 10 minutes, 40 a day (a question to both models is 2) | counters |
| Answers per model per day | 300 | counter |

A wake takes its whole possible cost (rate times minutes) from the budget first, and gets it back only when nothing started. Stopping early gives nothing back, so at $4.85 an hour the default buys 2 wakes a day. Everything under "Run it" still applies on top: the live count, one per model, the idle stop, the sweep, `HOST_TUNED_DAILY_USD` and `DAILY_SPEND_CAP_USD`. Wakes never use Lambda. The owner token is dropped, so a visitor has only this box. Day counters sit at the end of the UTC day (`dayWindow`), because the hourly prune deletes any window that began over an hour ago.

A visitor sends only user and assistant turns. The system message is the server's, from the job's `system` metric, and when the job has none no system message is sent. The base answer needs a provider that serves it: Fireworks says it can't. Asleep, waking, awake and going to sleep each have their own words, and a scaled-to-zero answer that returns "waking" moves the box back to waking.

## Export a tuned model (EXPORT_TUNED, off by default)

`/models/{id}` offers one download per device kind, from `GET /api/models/{id}/export?kind=mac|windows|linux|jetson_orin_nano`. Code: `lib/train/export`. Which file a kind gets is `deviceModelTarget`'s, so a Jetson gets one-bit Glimmer, every other kind the small Llama, and a tune on one base offers only that base's devices. Only public files at a pinned commit qualify.

Each row and each script says how far that script has really run (`proof` in `EXPORT_KINDS`). The script checks the OS and free disk, downloads the GGUF by commit, checks its sha256, deletes anything that fails, gets llama.cpp at b11669 (the job's own tag, with GitHub's asset digests pinned in `lib/train/export/llama-pins.ts`) and starts a chat. It writes the system message to a file, so nothing reaches a shell. Options: `--ollama`, `--check-only`, `--prompt`, `--max-tokens`, `--gpu-layers`, and on a Jetson `--cpu`. Windows takes `-Ollama`, `-CheckOnly`, `-Prompt`, `-MaxTokens`, `-GpuLayers`. A Jetson builds from the pinned source with CUDA, since no prebuilt has it for that board.

**Seen working:** the Mac script on `ggml-org/tiny-llamas` `stories260K.gguf` (1.2 MB) on an Apple silicon Mac, end to end with real llama.cpp. The Linux script's download and checks, with real pinned files and a stubbed OS name. **Simulated:** Linux and Jetson running, Ollama, the board check. **Not run:** the Windows script at all (a syntax check was denied here), any tuned file, a real Linux PC, a real board, and Ollama itself.
