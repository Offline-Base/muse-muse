# Muse Code recipe demos

The live demos for the cookbook's "Building with Muse Code" recipes (`lib/docs/demos/muse-code-cookbook.ts`). These recipes run in a terminal with the `muse` CLI, so each demo is a simulator built from its recipe's own formats (session logs, golden fixtures, shell stages, sandbox policy, cron), plus a live Muse Spark call where one helps. Every component is a client component with plain JSON props; the docs page adds `slug`.

| Component | Page | What it does | Live call |
|---|---|---|---|
| `RecipeBrowser` | cookbook/muse-code | The ten recipes, filtered by theme or search, with time, commands and the guarantee each proves | "Find recipes": strict JSON whose `slug` enum is the catalog, so picks are real recipes |
| `SessionLogExplorer` | cookbook/audit-agent-sessions | A real `muse exec --json` log (or two excerpts rebuilt from the recipe, or the reader's own session.jsonl, read locally): timeline in lanes, ledger, approval chain, a kill slider with what `muse resume` would find, the export header (the recipe's keys; turn and step counts are this demo's), redaction, and same-flags versus raw-against-redacted comparisons | "Review this session": the ledger summary (redacted, never the raw log) to a reviewer, strict JSON |
| `ReplayLab` | cookbook/deterministic-replay | The recipe's fixture in an editor (6 records against the committed file's 7), `muse trace inspect` and `replay_gate.sh` run offline, drift and failure presets, an illustration of byte-determinism | "Record a live run", then author a fixture from it |
| `ContainmentChecker` | cookbook/contained-execution | Launch flags and probe result, the five contract steps, the recipe's three boundaries with their exact errors | The model calls `bash` inside the simulated sandbox, on the recipe's workspace, and reports |
| `GuardrailTester` | cookbook/immutable-guardrails | Both checks (mediated write, OS sandbox) for any path, route and flags; the review offers only allow_once or abort | The model gets `edit_file` and `bash` on the recipe's workspace with its rules loaded; you answer the review, and allowed edits change the files for the rest of the run |
| `StageSplitter` | cookbook/staged-approvals | Compound command to stages, on-request or untrusted mode, granted rules with the recipe's precedence, the three-scope prompt, the log's jq output, the intent (authorization only) and the approval event's stage_evidence | The model's `bash` call goes through the same stages |
| `FanoutPlanner` | cookbook/subagent-fanout | A board of worktree-isolated children with the concurrency limit, queued or interrupting steers, cooperative cancels | "Plan the fan-out": tasks, files, checks and merge order as strict JSON |
| `GoalJudge` | cookbook/goal-tracking | `/goal`, the status line, the step probe | A judge grades each check with a quote; the page gates `update_goal` on every check proven |
| `SkillExplorer` | cookbook/bundled-skills | The four skills and their loading contract | The recipe's prompt in the skill's style: a streamed plan, one question at a time (with DECISIONS.md records), or the /taste mapping |
| `ScheduleBuilder` | cookbook/loop-and-cron | A local cron validator: words, next fire times in the browser's timezone, jitter window, seven-day lifetime, a session-scoped job list (next eligible fire shown as its window) with recovery | A `/loop` request to the stored job as strict JSON |
| `SideChat` | cookbook/side-chats | Two lanes, the side branch from the main thread's last committed response | Every turn streams on Responses with `previous_response_id` |

Shared pieces: `AgentLoopPanel` (the model plus a page's simulated harness, which can stop and ask the reader; `onStart` resets the harness's working tree; a reply cut off at the token limit is flagged on its step, never shown as the report), `hooks.ts` (`useStrictJson`, `useAgentLoop`), `parts.tsx` (`Terminal`, with `wrap={false}` for column output, `Argv`, `Steps`, `Verdict`, `Chip`, `ShowCode`, `Section`), `mcc.module.css`.

Pure logic in `logic/`, all tested: `session-log` (envelopes, lanes, ledger, approvals, resume, diagnostics, redaction, jq views), `samples` and `exec-sample` (the real log, byte for byte from docs/spikes/muse-exec-sample.jsonl), `replay`, `shell` (the stage parser), `approvals` (with the staged recipe's workspace), `sandbox` (each workspace's files: ls, cat, head, tail, wc, grep, test, git status and script output answer from them, landed writes change a run's tree, and a command it can't answer says so in the tool result), `guardrails` (the guardrail recipe's workspace), `cron`, `fanout`, `goal`, `recipes`, `skills`, `live` (strict JSON and tool-loop bodies, reply readers, `unfinishedReply`, and retries after 1.5, 3 and 5 s when Meta can't find a just-finished `previous_response_id`), and `requests` (every live request body, shared by the components, the tests and the proxy checks).

Where a recipe doesn't show a format (the full approval window, a policy-allow resolution name, approval-policy.json's shape, stage_evidence's fields, the allowed decision value), the demos say they're filling in, and live runs follow this demo's summary of a skill rather than Muse Code's own SKILL.md.

Tests: `npx tsx --test --experimental-test-module-mocks components/docs/playgrounds/muse-code-cookbook/__tests__/*.test.ts components/docs/playgrounds/muse-code-cookbook/__tests__/*.test.tsx`

The copy prompts in `lib/docs/demos/muse-code-cookbook.ts` keep each snippet under 1,000 characters and leave room for "Include what I just ran", so the kit trims only the recorded request: `__tests__/prompts.test.ts` checks every page, agent and language with the page's own recorded request and a worst-case one.
